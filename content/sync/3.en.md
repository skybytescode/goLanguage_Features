# Sync and atomic — Advanced

The rules that make synchronized code correct: the `WaitGroup` contract, lock ordering, `RWMutex`'s writer preference, the memory model's guarantees for atomic operations, and sharding.

## The `WaitGroup` contract

- `Add` with a positive number must happen **before** `Wait` and before the goroutine starts; otherwise `Wait` may see the counter at 0 and return too early. `wg.Go` (Go 1.25) removes this whole class of mistakes.
- The counter must never go negative: an extra `Done` panics.
- A `WaitGroup` can be reused, but only after the previous `Wait` has returned.
- It must not be copied after first use (`go vet` checks).

## Lock ordering

Two goroutines taking the same two mutexes in different orders can block each other forever:

```go,ignore
// goroutine 1           // goroutine 2
a.mu.Lock()              b.mu.Lock()
b.mu.Lock() // waits     a.mu.Lock() // waits: deadlock
```

Fixes: a fixed global order (for example by object ID), a single lock for operations touching several objects, or restructuring the code so it never holds two locks at once. The runtime only detects **global** deadlock (every goroutine blocked); a partial deadlock between two goroutines in a running server goes unnoticed until the `goroutine` profile shows them stuck in `sync.(*Mutex).Lock`.

## `RWMutex`: writer preference

When a writer calls `Lock`, it announces its intent (it subtracts a large constant from `readerCount`); **new readers** block immediately, even while other readers are still reading. The writer only waits for existing readers. This prevents writer starvation, but has a consequence: **recursive `RLock` can deadlock**:

```go,ignore
func (c *Cache) A() {
	c.mu.RLock()
	defer c.mu.RUnlock()
	c.B() // if a writer requested Lock in between, the RLock in B blocks forever
}

func (c *Cache) B() {
	c.mu.RLock()
	defer c.mu.RUnlock()
}
```

## The memory model and `atomic`

Since 2022, Go's memory model states explicitly: operations in `sync/atomic` are **sequentially consistent** — they behave as if executed in a single global order consistent with each goroutine's order. If the effect of atomic operation A is observed by atomic operation B, then A happens before B.

This means an atomic flag can "publish" data written normally:

```go
package main

import (
	"fmt"
	"sync/atomic"
	"time"
)

var (
	data  []int       // written normally
	ready atomic.Bool // publication
)

func main() {
	go func() {
		data = []int{1, 2, 3}
		ready.Store(true) // the write to data happens before
	}()
	for !ready.Load() {
		time.Sleep(time.Millisecond)
	}
	fmt.Println(data) // guaranteed [1 2 3]
}
```

Go doesn't expose weaker orderings (acquire/release, relaxed) like C++ or Rust; the simplicity costs little on x86 (where loads are ordered anyway) and somewhat more on ARM.

The `atomic.Int64` & co. types also guarantee **64-bit alignment** on 32-bit platforms — the reason they're preferred over the old `atomic.AddInt64(&x, 1)` functions.

## Sharding

When a single mutex becomes the hot spot, split the data into N shards, each with its own mutex, chosen by the key's hash. Contention drops roughly N-fold, at the cost of more complicated global operations (counting, iterating).

## Summary

- `Add` before `go` and before `Wait` — or, more simply, `wg.Go`.
- Always take multiple locks in the same global order.
- `RWMutex` prefers writers; recursive `RLock` can deadlock.
- Atomics are sequentially consistent and can publish normally written data.
- Sharding divides contention by N.
