# Sync și atomic — Avansat

Regulile care fac codul sincronizat corect: contractul lui `WaitGroup`, ordinea lock-urilor, preferința lui `RWMutex` pentru scriitori, garanțiile modelului de memorie pentru operațiile atomice și sharding-ul.

## Contractul lui `WaitGroup`

- `Add` cu un număr pozitiv trebuie să se întâmple **înainte** de `Wait` și înainte de pornirea goroutine-ului; altfel `Wait` poate vedea contorul la 0 și se poate întoarce prea devreme. `wg.Go` (Go 1.25) elimină complet această clasă de greșeli.
- Contorul nu are voie să devină negativ: un `Done` în plus dă panic.
- Un `WaitGroup` poate fi refolosit, dar doar după ce `Wait`-ul anterior s-a întors.
- Nu se copiază după prima folosire (`go vet` verifică).

## Ordinea lock-urilor

Două goroutines care iau aceleași două mutex-uri în ordini diferite se pot bloca reciproc pentru totdeauna:

```go,ignore
// goroutine 1           // goroutine 2
a.mu.Lock()              b.mu.Lock()
b.mu.Lock() // așteaptă  a.mu.Lock() // așteaptă: deadlock
```

Soluții: o ordine globală fixă (de exemplu după ID-ul obiectului), un singur lock pentru operațiile care ating mai multe obiecte, sau restructurarea codului astfel încât să nu țină niciodată două lock-uri simultan. Runtime-ul detectează doar deadlock-ul **global** (toate goroutines blocate); un deadlock parțial între două goroutines într-un server activ trece neobservat până când profilul `goroutine` le arată blocate în `sync.(*Mutex).Lock`.

## `RWMutex`: preferință pentru scriitori

Când un scriitor cheamă `Lock`, el anunță intenția (scade `readerCount` cu o constantă mare); **cititorii noi** se blochează imediat, chiar dacă alți cititori încă citesc. Scriitorul așteaptă doar cititorii existenți. Asta previne înfometarea scriitorilor, dar are o consecință: **`RLock` recursiv poate face deadlock**:

```go,ignore
func (c *Cache) A() {
	c.mu.RLock()
	defer c.mu.RUnlock()
	c.B() // dacă între timp un scriitor a cerut Lock, RLock-ul din B blochează pentru totdeauna
}

func (c *Cache) B() {
	c.mu.RLock()
	defer c.mu.RUnlock()
}
```

## Modelul de memorie și `atomic`

Din 2022, modelul de memorie Go specifică explicit: operațiile din `sync/atomic` sunt **secvențial consistente** — se comportă ca și cum ar fi executate într-o ordine globală unică, consistentă cu ordinea din fiecare goroutine. Dacă efectul unei operații atomice A e observat de operația atomică B, atunci A se întâmplă înaintea lui B.

Asta înseamnă că un flag atomic poate „publica” date scrise normal:

```go
package main

import (
	"fmt"
	"sync/atomic"
	"time"
)

var (
	date []int       // scris normal
	gata atomic.Bool // publicare
)

func main() {
	go func() {
		date = []int{1, 2, 3}
		gata.Store(true) // scrierea lui date se întâmplă înainte
	}()
	for !gata.Load() {
		time.Sleep(time.Millisecond)
	}
	fmt.Println(date) // garantat [1 2 3]
}
```

Go nu expune ordonări mai slabe (acquire/release, relaxed) ca C++ sau Rust; simplitatea costă puțin pe x86 (unde load-urile sunt oricum ordonate) și ceva mai mult pe ARM.

Tipurile `atomic.Int64` & co. garantează și **alinierea la 64 de biți** pe platformele de 32 de biți — motivul pentru care sunt preferate funcțiilor vechi `atomic.AddInt64(&x, 1)`.

## Sharding

Când un singur mutex devine punctul fierbinte, împarte datele în N bucăți, fiecare cu mutex-ul ei, alese după hash-ul cheii. Contenția scade aproximativ de N ori, cu prețul unor operații globale (numărare, iterare) mai complicate.

## Pe scurt

- `Add` înainte de `go` și de `Wait` — sau, mai simplu, `wg.Go`.
- Ia mai multe lock-uri mereu în aceeași ordine globală.
- `RWMutex` preferă scriitorii; `RLock` recursiv poate bloca.
- Atomicele sunt secvențial consistente și pot publica date scrise normal.
- Sharding-ul împarte contenția la N.
