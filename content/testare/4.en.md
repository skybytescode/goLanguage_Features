# Testing, benchmarks and fuzzing — Expert

What `go test` does under the hood: the generated test binary, the `synctest` bubble and its fake clock, the result cache, and coverage for whole binaries.

## The test binary

`go test` doesn't run the tests "directly". For each package, it:

1. compiles the package together with its `_test.go` files (internal tests) and, separately, the `pkg_test` package (external tests);
2. **generates** a `main` package (`_testmain.go`) holding lists of every `Test*`, `Benchmark*`, `Fuzz*` and `Example*` function found, and calls `testing.MainStart`;
3. links everything into a `pkg.test` executable and runs it, with flags prefixed by `-test.` (`-test.run`, `-test.v`).

```bash
go test -c -o calc.test ./calc        # only build the binary
./calc.test -test.run TestAdd -test.v
go test -exec 'sudo' ./...            # run the binary through another program
go test -json ./... | tee results.json   # structured events, for CI
```

A `func TestMain(m *testing.M)` in the package replaces the generated entry point: useful for global setup (a database started once), as long as it calls `m.Run()` and returns its exit code.

## Inside the `synctest` bubble

`synctest.Test` starts the function in a new goroutine marked as belonging to a **bubble**. Every goroutine started from it belongs to the same bubble. The bubble has its own **clock**, which starts at midnight UTC on January 1, 2000 and doesn't advance on its own.

The runtime tracks whether every goroutine in the bubble is **durably blocked** — blocked in operations only other goroutines in the bubble can unblock: operations on channels created in the bubble, `time.Sleep`, `sync.WaitGroup.Wait`, `sync.Cond.Wait`, `select` on such channels. When that happens:

- if there are timers in the bubble, the clock **jumps** straight to the next timer, which fires;
- if there are no timers, the test is **deadlocked** and fails with an explicit message.

Operations waiting on something outside the bubble (real network I/O, mutexes, channels created outside the bubble) are **not** durable blocking: the bubble can't advance time while a goroutine sits in them. That's why code tested with `synctest` uses `net.Pipe` or in-memory implementations instead of the real network.

## The test cache

`go test` keeps the results of passing tests and reuses them (`(cached)` in the output) if nothing changed: the sources, the flags, the environment variables **read** by the test and the files **opened** by the test (tracked through `os.Open`, `os.Stat`, etc.). Results are only cached in package-list mode (`go test ./...`), not in local-directory mode (plain `go test`). `-count=1` disables the cache.

## Coverage for whole binaries (Go 1.20)

Coverage isn't limited to unit tests. A binary built with `-cover` writes coverage data on exit, useful for integration or end-to-end tests:

```bash
go build -cover -o app ./cmd/app
GOCOVERDIR=./coverage ./app --scenario=full
go tool covdata percent -i=./coverage
go tool covdata textfmt -i=./coverage -o profile.txt   # then go tool cover -html
```

## The race detector under the hood

`-race` builds the program with **ThreadSanitizer** (TSan, from LLVM): the compiler inserts an instrumentation call before every memory access, and the runtime reports every synchronization operation (channels, mutexes, atomics, `go`, `WaitGroup`) to TSan.

For each word of memory, TSan keeps **shadow memory** with the most recent accesses: which goroutine, at what logical time (a **vector clock** per goroutine), read or write. On every new access it compares against the old ones: if two accesses, at least one a write, aren't ordered by any happens-before relation, it reports a race, with both stack traces.

Practical consequences:

- a 2–20× slowdown and 5–10× more memory: it runs in tests and CI, rarely in production;
- it only detects races that **actually happen** in the observed execution; code not covered by tests can hide races;
- it has no false positives: every report is a real race, even if it "looks harmless";
- it's available on the main platforms (linux, darwin, windows, freebsd on amd64/arm64) and needs cgo on some of them.

```bash
go test -race ./...
GORACE="halt_on_error=1 history_size=4" go test -race ./...   # stop at the first race, longer history
```

## Summary

- `go test` generates a `main` with every test and builds a `pkg.test` binary.
- `TestMain` replaces the entry point for global setup.
- `synctest` advances a fake clock when every goroutine in the bubble is durably blocked.
- The test cache accounts for the files and environment variables a test reads.
- `-cover` and `GOCOVERDIR` for whole-binary coverage.
- `-race` uses ThreadSanitizer: shadow memory and vector clocks; it only finds races that occur.
