# Testare, benchmarks și fuzzing — Expert

Ce face `go test` pe dinăuntru: binarul de test generat, bula din `synctest` și ceasul ei fals, cache-ul de rezultate și acoperirea pentru binare întregi.

## Binarul de test

`go test` nu rulează testele „direct”. Pentru fiecare pachet:

1. compilează pachetul împreună cu fișierele `_test.go` (testele interne) și, separat, pachetul `pkg_test` (testele externe);
2. **generează** un pachet `main` (`_testmain.go`) care conține liste cu toate funcțiile `Test*`, `Benchmark*`, `Fuzz*` și `Example*` găsite, și apelează `testing.MainStart`;
3. leagă totul într-un executabil `pkg.test` și îl rulează, cu flag-urile prefixate cu `-test.` (`-test.run`, `-test.v`).

```bash
go test -c -o calcul.test ./calcul    # doar construiește binarul
./calcul.test -test.run TestAduna -test.v
go test -exec 'sudo' ./...            # rulează binarul printr-un alt program
go test -json ./... | tee rezultate.json   # evenimente structurate, pentru CI
```

Un `func TestMain(m *testing.M)` în pachet înlocuiește punctul de intrare generat: util pentru setup global (o bază de date pornită o singură dată), cu condiția să apeleze `m.Run()` și să întoarcă codul lui de ieșire.

## Bula din `synctest` pe dinăuntru

`synctest.Test` pornește funcția într-o goroutine nouă, marcată ca aparținând unei **bule**. Toate goroutines pornite din ea aparțin aceleiași bule. Bula are propriul **ceas**, care pornește la miezul nopții UTC din 1 ianuarie 2000 și nu avansează singur.

Runtime-ul urmărește dacă toate goroutines din bulă sunt **blocate durabil** — blocate în operații pe care doar alte goroutines din bulă le pot debloca: operații pe channels create în bulă, `time.Sleep`, `sync.WaitGroup.Wait`, `sync.Cond.Wait`, `select` pe astfel de channels. Când se întâmplă asta:

- dacă există timere în bulă, ceasul **sare** direct la următorul timer, care se declanșează;
- dacă nu există timere, testul e într-un **deadlock** și eșuează cu un mesaj explicit.

Operațiile care așteaptă ceva din afara bulei (I/O de rețea reală, mutex-uri, channels create în afara bulei) **nu** sunt blocări durabile: bula nu poate avansa timpul cât timp o goroutine stă în ele. De aceea, codul testat cu `synctest` folosește `net.Pipe` sau implementări în memorie în locul rețelei reale.

## Cache-ul de teste

`go test` păstrează rezultatele testelor care au trecut și le refolosește (`(cached)` în output) dacă nu s-a schimbat nimic: sursele, flag-urile, variabilele de mediu **citite** de test și fișierele **deschise** de test (urmărite prin `os.Open`, `os.Stat` etc.). Rezultatele se cache-uiesc doar în modul listă de pachete (`go test ./...`), nu în modul director curent (`go test` simplu). `-count=1` dezactivează cache-ul.

## Acoperirea pentru binare întregi (Go 1.20)

Acoperirea nu e limitată la teste unitare. Un binar construit cu `-cover` scrie date de acoperire la ieșire, util pentru teste de integrare sau end-to-end:

```bash
go build -cover -o app ./cmd/app
GOCOVERDIR=./acoperire ./app --scenariu=complet
go tool covdata percent -i=./acoperire
go tool covdata textfmt -i=./acoperire -o profil.txt   # apoi go tool cover -html
```

## Detectorul de curse pe dinăuntru

`-race` compilează programul cu **ThreadSanitizer** (TSan, din LLVM): compilatorul inserează un apel de instrumentare înaintea fiecărui acces la memorie, iar runtime-ul raportează la TSan fiecare operație de sincronizare (channels, mutex-uri, atomice, `go`, `WaitGroup`).

TSan ține, pentru fiecare cuvânt de memorie, o **memorie umbră** cu ultimele accese: ce goroutine, în ce moment logic (un **ceas vectorial** per goroutine), citire sau scriere. La fiecare acces nou compară cu cele vechi: dacă două accese, cel puțin unul o scriere, nu sunt ordonate de nicio relație happens-before, raportează o cursă, cu stack trace-urile ambelor.

Consecințe practice:

- încetinire de 2–20 de ori și memorie de 5–10 ori mai multă: se rulează în teste și CI, rar în producție;
- detectează doar cursele care **chiar se întâmplă** în execuția observată; codul neacoperit de teste poate ascunde curse;
- nu are rezultate fals pozitive: orice raport e o cursă reală, chiar dacă „pare inofensivă”;
- e disponibil pe platformele principale (linux, darwin, windows, freebsd pe amd64/arm64) și cere cgo pe unele dintre ele.

```bash
go test -race ./...
GORACE="halt_on_error=1 history_size=4" go test -race ./...   # oprire la prima cursă, istoric mai lung
```

## Pe scurt

- `go test` generează un `main` cu toate testele și construiește un binar `pkg.test`.
- `TestMain` înlocuiește punctul de intrare pentru setup global.
- `synctest` avansează un ceas fals când toate goroutines din bulă sunt blocate durabil.
- Cache-ul de teste ține cont de fișierele și variabilele de mediu citite.
- `-cover` și `GOCOVERDIR` pentru acoperirea binarelor întregi.
- `-race` folosește ThreadSanitizer: memorie umbră și ceasuri vectoriale; găsește doar cursele care se produc.
