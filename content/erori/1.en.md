# Errors, defer, panic and recover — Fundamentals

Go has no exceptions. A function that can fail returns an **error** as an ordinary value, and the caller checks it explicitly. On top of that, `defer` schedules cleanup code, and `panic` stops the program in truly unexpected situations.

## The `error` type

`error` is an interface with a single method:

```go,ignore
type error interface {
	Error() string
}
```

A function that can fail returns, by convention, the error as its **last** result. `nil` means "no error".

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	n, err := strconv.Atoi("12a")
	if err != nil {
		fmt.Println("conversion failed:", err)
		return
	}
	fmt.Println("number:", n)
}
```

`if err != nil` is the most common pattern in Go. It's repetitive, but it makes every place where something can fail visible.

## Creating errors

```go
package main

import (
	"errors"
	"fmt"
)

func withdraw(balance, amount int) (int, error) {
	if amount <= 0 {
		return balance, errors.New("amount must be positive")
	}
	if amount > balance {
		return balance, fmt.Errorf("insufficient funds: you have %d, asking for %d", balance, amount)
	}
	return balance - amount, nil
}

func main() {
	balance, err := withdraw(100, 150)
	if err != nil {
		fmt.Println("error:", err)
	}
	fmt.Println("balance:", balance)
}
```

- `errors.New` for a fixed message.
- `fmt.Errorf` for a message with values.

Error messages start with a lowercase letter and don't end with a period: they usually end up in the middle of other messages.

## Don't ignore errors

An ignored error hides the problem and moves it further along, where it's hard to find. If you ignore an error on purpose, make it visible with `_`:

```go,ignore
_ = file.Close() // we know we don't care about this error here
```

## `defer`: runs when the function exits

`defer` postpones a call until the current function returns, no matter which path it takes. It's the natural place for cleanup: closing files, unlocking mutexes.

```go
package main

import "fmt"

func main() {
	fmt.Println("start")
	defer fmt.Println("cleanup") // runs last
	fmt.Println("work")
}
```

Several `defer`s run in **reverse** order (last in, first out):

```go
package main

import "fmt"

func main() {
	for i := range 3 {
		defer fmt.Println("defer", i)
	}
	fmt.Println("done")
	// done, defer 2, defer 1, defer 0
}
```

The typical pattern: open a resource, check the error, then immediately schedule the close:

```go,ignore
f, err := os.Open("data.txt")
if err != nil {
	return err
}
defer f.Close()
// use f...
```

## `panic`

`panic` stops normal execution. Deferred functions still run, then the program exits with a message and a stack trace. The runtime itself panics on programming errors: an index out of range, a `nil` pointer, integer division by zero.

```go,panic
package main

import "fmt"

func main() {
	defer fmt.Println("the defer runs on panic too")
	s := []int{1, 2, 3}
	i := 5
	fmt.Println(s[i]) // panic: runtime error: index out of range [5] with length 3
}
```

The rule: **errors** are for expected situations (missing file, invalid input, network down). **panic** is for bugs and impossible situations.

## `recover`

`recover`, called inside a deferred function, stops a panic and returns its value. The program continues after the function that panicked:

```go
package main

import "fmt"

func safely(f func()) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught:", r)
		}
	}()
	f()
}

func main() {
	safely(func() { panic("something bad") })
	fmt.Println("the program goes on")
}
```

You'll rarely use it: for example, an HTTP server uses it so a request that panics doesn't take down the whole server.

## Summary

- Errors are values; check them with `if err != nil`.
- `errors.New` and `fmt.Errorf` create errors.
- `defer` runs when the function exits, in reverse order.
- `panic` is for bugs, not ordinary errors.
- `recover` stops a panic, only from inside a `defer`.
