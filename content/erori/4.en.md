# Errors, defer, panic and recover — Expert

What the runtime does on a `panic`: the `_defer` and `_panic` records, stack unwinding, how `recover` stops the unwinding, the difference from fatal errors, and what errors concretely cost.

## How `panic` works in the runtime

`panic(v)` calls `runtime.gopanic`, which:

1. creates a `_panic` record (the value, a link to an earlier panic) and puts it on the goroutine's list;
2. walks the goroutine's deferred functions, most recent first, and runs them in turn;
3. if one of them calls `recover`, the runtime marks the panic as recovered; once the deferred function returns, execution **resumes at the normal exit** of the function that contained that `defer`, as if it had executed `return`;
4. if there are no deferred functions left, it prints the value and the stack trace and ends the process with exit code 2.

Deferred functions can live in two places: linked `_defer` records (for `defer` in loops) or **open-coded defers**, where the compiler generated the calls directly at the function's exits (see [Functions](../../functii/4/)). For the latter, on panic the runtime reads a bitmap of active `defer`s from the function's metadata (`funcdata`) and runs them in the right order.

The rule "`recover` only when called directly by the deferred function" comes from the implementation: `recover` compares the caller's stack pointer with the one recorded in `_panic` and returns the value only if they match.

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func deep(n int) {
	if n == 0 {
		panic("from the bottom")
	}
	deep(n - 1)
}

func main() {
	defer func() {
		r := recover()
		fmt.Println("recovered:", r)
		fmt.Printf("%s", debug.Stack()) // the stack is still the one from the panic
	}()
	deep(3)
}
```

Inside the deferred function, the stack **hasn't been unwound yet**: `debug.Stack()` shows the frames down to where the panic happened. Only after returning from the `defer` does the runtime skip over them.

## Fatal errors: can't be recovered

Some situations aren't panics but **fatal runtime errors**; `recover` doesn't see them, and the program stops immediately:

| Fatal error | Cause |
|---|---|
| `concurrent map writes` | simultaneous writes to a map, unsynchronized |
| `all goroutines are asleep - deadlock!` | no goroutine can make progress |
| `stack overflow` | recursion too deep |
| `out of memory` | allocation impossible |

```go,panic
package main

func main() {
	defer func() { recover() }() // useless: the deadlock is fatal
	ch := make(chan int)
	<-ch // fatal error: all goroutines are asleep - deadlock!
}
```

## The cost of errors

Creating an error with `errors.New` or `fmt.Errorf` allocates (and `fmt.Errorf` also formats). On hot paths where the error is frequent and "normal" (for example a parser trying several alternatives), use preallocated sentinels instead of new errors on every call. An `if err != nil` on the success path costs practically nothing: it's a comparison with zero, and branch prediction gets it right almost every time.

## Summary

- `gopanic` runs the deferred functions (`_defer` records or open-coded, via `funcdata`).
- `recover` stops the unwinding; execution resumes at the exit of the function with the `defer`.
- Inside `defer`, the stack is still intact: the right place to log the stack trace.
- Fatal errors (concurrent map writes, deadlock, stack overflow) bypass this mechanism.
- Errors allocate when created; on hot paths, use preallocated sentinels.
