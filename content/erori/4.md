# Erori, defer, panic și recover — Expert

Ce face runtime-ul la un `panic`: înregistrările `_defer` și `_panic`, derularea stivei, cum oprește `recover` derularea, diferența față de erorile fatale și cât costă, concret, erorile.

## Cum funcționează `panic` în runtime

`panic(v)` apelează `runtime.gopanic`, care:

1. creează o înregistrare `_panic` (valoarea, legătura la un panic anterior) și o pune în lista goroutine-ului;
2. parcurge funcțiile amânate ale goroutine-ului, de la cea mai recentă, și le rulează pe rând;
3. dacă una dintre ele apelează `recover`, runtime-ul marchează panic-ul ca recuperat; după ce funcția amânată se întoarce, execuția **continuă la ieșirea normală** a funcției care conținea acel `defer`, ca și cum ar fi executat `return`;
4. dacă nu mai sunt funcții amânate, afișează valoarea și stack trace-ul și termină procesul cu codul 2.

Funcțiile amânate pot fi găsite în două locuri: înregistrări `_defer` legate în listă (pentru `defer` în bucle) sau **open-coded defers**, unde compilatorul a generat apelurile direct la ieșirile din funcție (vezi [Funcții](../../functii/4/)). Pentru acestea din urmă, la panic runtime-ul citește din metadatele funcției (`funcdata`) un bitmap cu `defer`-urile active și le rulează în ordinea corectă.

Regula „`recover` doar apelat direct din funcția amânată” vine din implementare: `recover` compară pointerul de stivă al apelantului cu cel înregistrat în `_panic` și întoarce valoarea doar dacă se potrivesc.

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func adanc(n int) {
	if n == 0 {
		panic("de la fund")
	}
	adanc(n - 1)
}

func main() {
	defer func() {
		r := recover()
		fmt.Println("recuperat:", r)
		fmt.Printf("%s", debug.Stack()) // stiva e încă cea din momentul panic-ului
	}()
	adanc(3)
}
```

În funcția amânată, stiva **nu a fost încă derulată**: `debug.Stack()` arată cadrele până la locul panic-ului. Abia după întoarcerea din `defer` runtime-ul sare peste ele.

## Erori fatale: nu pot fi recuperate

Unele situații nu sunt panic-uri, ci **erori fatale** ale runtime-ului; `recover` nu le vede, iar programul se oprește imediat:

| Eroare fatală | Cauză |
|---|---|
| `concurrent map writes` | scrieri simultane într-un map, fără sincronizare |
| `all goroutines are asleep - deadlock!` | nicio goroutine nu mai poate avansa |
| `stack overflow` | recursie prea adâncă |
| `out of memory` | alocare imposibilă |

```go,panic
package main

func main() {
	defer func() { recover() }() // inutil: deadlock-ul e fatal
	ch := make(chan int)
	<-ch // fatal error: all goroutines are asleep - deadlock!
}
```

## Costul erorilor

Crearea unei erori cu `errors.New` sau `fmt.Errorf` alocă (și `fmt.Errorf` formatează). Pe drumuri fierbinți în care eroarea e frecventă și „normală” (de exemplu un parser care încearcă mai multe variante), folosește santinele pre-alocate în loc de erori noi la fiecare apel. Un `if err != nil` pe drumul fără eroare costă practic nimic: e o comparație cu zero, iar predicția de salt o ghicește aproape mereu.

## Pe scurt

- `gopanic` rulează funcțiile amânate (înregistrări `_defer` sau open-coded, prin `funcdata`).
- `recover` oprește derularea; execuția continuă la ieșirea funcției cu `defer`-ul.
- În `defer`, stiva e încă intactă: e locul potrivit pentru logarea stack trace-ului.
- Erorile fatale (map concurent, deadlock, stack overflow) nu trec prin acest mecanism.
- Erorile alocă la creare; pe drumuri fierbinți, folosește santinele pre-alocate.
