# Funcții și closures — Expert

Ce se întâmplă la un apel de funcție în Go: convenția de apel bazată pe registre, inlining-ul, cum sunt reprezentate closure-urile, cum cresc stivele goroutine-urilor și cum a devenit `defer` aproape gratuit.

## Convenția de apel: registre (ABIInternal)

Din Go 1.17 (amd64) și 1.18 (arm64, ppc64, riscv64), argumentele și rezultatele sunt transmise prin **registre**, nu prin stivă. Câștigul tipic a fost de aproximativ 5% la viteză și o reducere a dimensiunii binarelor.

Codul scris în assembly folosește în continuare vechea convenție, **ABI0** (totul pe stivă); compilatorul generează automat funcții „wrapper” între cele două. De aceea, la profilare, poți vedea simboluri cu sufixul `.abi0`.

## Inlining

Compilatorul copiază corpul funcțiilor mici în locul apelului. Asta elimină costul apelului, dar mai ales permite alte optimizări (propagarea constantelor, escape analysis mai precisă, eliminarea verificărilor de limite).

O funcție e candidată dacă „costul” ei, măsurat în noduri din arborele sintactic, e sub un buget (80). Vezi deciziile compilatorului cu `-gcflags=-m`:

```bash
$ go build -gcflags=-m ./...
./main.go:5:6: can inline aduna
./main.go:12:13: inlining call to aduna
./main.go:9:6: cannot inline proceseaza: function too complex: cost 112 exceeds budget 80
```

- `//go:noinline` deasupra unei funcții împiedică inlining-ul (util în benchmark-uri).
- Din Go 1.12 funcționează și inlining-ul „mid-stack”: o funcție care apelează alte funcții poate fi și ea inlined.
- Cu **PGO** (profile-guided optimization, Go 1.21+), pui un profil CPU în `default.pgo` lângă `main`; compilatorul mărește bugetul pentru apelurile „fierbinți” și **devirtualizează** apelurile prin interfețe când profilul arată un tip concret dominant.

## Cum arată un closure

O valoare de tip funcție e un pointer la o structură `funcval`: adresa codului, urmată de variabilele capturate.

```go,ignore
// pseudo-cod: ce generează compilatorul pentru un closure
type funcval struct {
	fn uintptr // adresa codului
	// urmează variabilele capturate: valori sau pointeri
}
```

La apel, adresa structurii e pusă într-un registru dedicat (`DX` pe amd64), prin care codul closure-ului își găsește variabilele.

O variabilă e capturată:

- **prin valoare**, dacă e mică (sub 128 de octeți) și nu se mai modifică după capturare;
- **prin referință** în rest. Variabila „scapă” atunci pe heap, ca să trăiască cât closure-ul.

```go
package main

import "fmt"

func main() {
	x := 1
	f := func() int { return x } // captură prin referință: x se modifică mai jos
	x = 2
	fmt.Println(f()) // 2, nu 1
}
```

O funcție anonimă care nu capturează nimic e doar un pointer static, fără alocare.

## Stive care cresc

Fiecare goroutine pornește cu o stivă mică (minim 2 KiB; din Go 1.19 dimensiunea inițială se adaptează la media stivelor observate). Fiecare funcție începe cu un **prolog** care compară pointerul de stivă cu limita; dacă nu mai e loc, apelează `runtime.morestack`.

Stiva nu crește prin „segmente” (cum era până la Go 1.3), ci **prin copiere**: runtime-ul alocă o stivă de două ori mai mare, copiază cadrele și ajustează toți pointerii care indică în stivă. Asta e posibil pentru că escape analysis garantează că nimic de pe heap nu indică în stiva unei goroutine.

Go nu face **tail call optimization**. O recursie foarte adâncă se oprește la limita maximă a stivei (1 GB pe 64 de biți, configurabilă cu `debug.SetMaxStack`), cu o eroare fatală, nu cu un panic care poate fi recuperat:

```go,panic
package main

import (
	"fmt"
	"runtime/debug"
)

func adanc(n int) int {
	var tampon [64]byte // face fiecare cadru mai mare
	tampon[0] = byte(n)
	return adanc(n+1) + int(tampon[0])
}

func main() {
	debug.SetMaxStack(1 << 20) // 1 MiB, ca exemplul să se termine repede
	fmt.Println(adanc(0))      // fatal error: stack overflow
}
```

## `defer` aproape gratuit

Până la Go 1.13, fiecare `defer` aloca o înregistrare. Din Go 1.14, **open-coded defers**: când o funcție are cel mult 8 `defer`-uri și niciunul nu e într-o buclă, compilatorul inserează direct apelurile la ieșirile din funcție, iar costul devine de ordinul nanosecundelor. Un `defer` într-o buclă cade înapoi pe mecanismul mai lent.

## Pe scurt

- Argumentele trec prin registre; assembly-ul folosește ABI0, cu wrapper-e.
- Inlining-ul are un buget; `-gcflags=-m` arată deciziile, PGO le îmbunătățește.
- Un closure e un `funcval`: cod + variabile capturate (prin valoare sau referință).
- Stivele cresc prin copiere; nu există tail call optimization.
- `defer` e open-coded când nu e în buclă.
