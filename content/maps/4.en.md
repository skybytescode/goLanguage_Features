# Maps — Expert

Since Go 1.24, maps are implemented as **Swiss tables**. We look at their structure, how they grow, why memory doesn't come back after `delete`, how the hash is computed, and how the runtime detects concurrent access.

## From buckets to Swiss tables

Up to Go 1.23, a map was an array of **buckets** of 8 pairs each, with chained overflow buckets and a load factor of 6.5. Growth doubled the array and moved elements gradually, on each later write ("incremental evacuation").

Go 1.24 replaced the implementation (package `internal/runtime/maps`) with a design inspired by Abseil:

```go,ignore
// simplified
type Map struct {
	used      uint64
	seed      uintptr  // the hash's random seed, per map
	directory []*table // extendible hashing
	// ...
}

type table struct {
	groups   groupsReference // groups of 8 slots each
	capacity uint16          // at most 1024 slots
	// ...
}

// a group: one control word (8 bytes) + 8 key/value slots
// each control byte: empty / deleted / full + 7 bits of the hash (H2)
```

On a lookup, the 64-bit hash is split into:

- **H1** (57 bits): selects the starting group; probing continues **quadratically** across groups;
- **H2** (7 bits): compared against all 8 control bytes **in a single operation** (SIMD on amd64, bit tricks elsewhere).

Only slots whose H2 matches are actually compared with the key. The result: fewer memory accesses, a higher load factor (7/8) and, in Go's benchmarks, operations 20–60% faster on large maps.

**Small** maps (at most 8 elements) are a single group, with no table and no directory.

## Growth: bounded per table

A table has at most 1024 slots. When one fills past 7/8, it's **doubled** if under the limit, otherwise **split** in two, and the directory (extendible hashing) doubles when needed. A single growth step therefore touches at most 1024 slots, which bounds the latency of an insert, without the old implementation's incremental evacuation.

Deleted slots become **tombstones** (a "deleted" marker), so probing doesn't stop early; they're reused by inserts and cleaned up at the next growth.

## Memory doesn't shrink after `delete`

A map **never shrinks**. Deleting every key keeps the tables allocated:

```go
package main

import (
	"fmt"
	"runtime"
)

func heapMiB() uint64 {
	runtime.GC()
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	return ms.HeapAlloc >> 20
}

func main() {
	m := make(map[int][64]byte)
	for i := range 500_000 {
		m[i] = [64]byte{}
	}
	fmt.Println("full:", heapMiB(), "MiB")

	for k := range m {
		delete(m, k)
	}
	fmt.Println("after delete:", heapMiB(), "MiB, len =", len(m)) // about the same

	m = nil
	fmt.Println("after m = nil:", heapMiB(), "MiB")
}
```

For caches that grow temporarily and then empty out, recreate the map (`m = make(map[K]V)`) instead of deleting keys. `clear(m)` behaves like `delete` on every key: it keeps the memory.

## Large keys and values

Keys and values larger than 128 bytes aren't stored directly in slots: the slot holds a pointer to a separate allocation. For large values, an explicit `map[K]*V` can be more efficient, but it adds GC pressure.

## The hash

Every map has a **random seed**, chosen at creation. It protects against collision attacks (input crafted so every key lands in the same place), and it's also why `range` order differs between maps and between runs. On CPUs with AES-NI, the hash for strings and bytes uses AES instructions.

The hash cost depends on the key: an `int` is cheap, a long `string` must be read in full, and an interface key (`map[any]V`) first requires looking up the dynamic type. The `hash/maphash` package (including `maphash.Comparable`, since Go 1.24) exposes the same algorithm for your own data structures.

## Detecting concurrent access

The map has a "being written" bit. A write sets it at the start and clears it at the end; any other operation that finds it set stops the program with `fatal error: concurrent map writes` or `concurrent map read and map write`. Detection is **opportunistic**: it only catches overlaps that actually happen, so the absence of the error doesn't prove correctness. `-race` does the full analysis.

The error is fatal, not a panic, because the internal structure may already be corrupted; continuing could silently produce wrong results.

## Summary

- Go 1.24+: Swiss tables with 8-slot groups, control bytes and H1/H2 probing.
- Growth is bounded to tables of at most 1024 slots.
- Maps don't shrink; recreate them after large deletions.
- A per-map random hash seed; keys and values over 128 bytes are stored indirectly.
- Concurrent-access detection is opportunistic and fatal; use `-race`.
