# Maps — Avansat

Deciziile de design din spatele map-urilor: de ce valoarea zero e citibilă dar nu și scriibilă, de ce nu poți lua adresa unui element, de ce ordinea e aleatoare intenționat și ce garantează specificația la iterare.

## Map-ul `nil`: citibil, dar nu scriibil

O variabilă map e un pointer la o structură din runtime. Valoarea zero e pointerul `nil`. Citirea dintr-un map `nil` e definită să se comporte ca dintr-un map gol (nu e nevoie de memorie pentru a răspunde „nu există”), dar o scriere ar avea nevoie de o structură unde să pună cheia — și nu are cum s-o creeze, pentru că ar trebui să modifice **variabila** apelantului, nu doar structura. De aceea scrierea dă panic, iar `make` e obligatoriu.

Aceeași logică explică de ce o funcție care primește un map **poate** adăuga chei (modifică structura comună), dar nu poate înlocui map-ul apelantului cu unul nou.

## De ce nu poți lua adresa unui element

`&m[k]` nu compilează. Motivul: la creștere, map-ul **mută** elementele în tabele noi. Un pointer luat înainte ar indica spre memorie veche, iar scrierile prin el s-ar pierde sau, mai rău, ar corupe alte date. Spre deosebire de slices — unde un pointer la un element vechi rămâne valid, doar spre alt array — aici runtime-ul nu ar putea garanta nici măcar siguranța memoriei.

Același motiv face ca `m[k].Camp = x` să nu compileze: ar cere adresa elementului.

## Ordinea aleatoare e o decizie de design

În primele versiuni, ordinea de iterare era stabilă „din întâmplare”, iar programele au început să depindă de ea. Când implementarea s-a schimbat, codul s-a stricat. Go 1.0 a făcut ordinea **intenționat aleatoare**: fiecare `range` pornește dintr-un punct ales aleatoriu. Așa, orice dependență de ordine apare imediat în teste, nu peste ani, la o schimbare de implementare. Trecerea la Swiss tables în Go 1.24 a fost posibilă tocmai pentru că nimeni nu putea depinde de ordinea vechii implementări.

```go
package main

import "fmt"

func main() {
	m := map[int]bool{1: true, 2: true, 3: true, 4: true, 5: true}
	for range 3 {
		for k := range m {
			fmt.Print(k, " ")
		}
		fmt.Println() // ordinea diferă, de obicei, de la o parcurgere la alta
	}
}
```

## Iterarea

Iteratorul pornește de la o poziție aleatoare și ține minte directorul de la început. Specificația garantează doar că:

- fiecare cheie existentă pe tot parcursul iterației apare exact o dată;
- o cheie ștearsă înainte să fie atinsă nu mai apare;
- o cheie adăugată în timpul iterației poate apărea sau nu.

Implementarea face ca aceste garanții să rămână valabile și când tabelele cresc sau se împart în timpul parcurgerii.

## Chei care surprind: `float` și interfețe

Egalitatea cheilor e `==`, cu toate ciudățeniile tipului:

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	m := map[float64]string{}
	m[0.0] = "zero"
	m[math.Copysign(0, -1)] = "minus zero" // -0 == +0: aceeași cheie
	fmt.Println(len(m), m[0])              // 1 minus zero

	nan := math.NaN()
	m[nan] = "a"
	m[nan] = "b" // NaN != NaN: fiecare inserare creează o cheie nouă
	_, gasit := m[nan]
	fmt.Println(len(m), gasit) // 3 false: cheile NaN nu pot fi găsite sau șterse cu delete

	clear(m) // Go 1.21: singura cale de a scăpa de cheile NaN
	fmt.Println(len(m))

	k := map[any]int{}
	k[1] = 1
	k[int64(1)] = 2     // alt tip dinamic: altă cheie
	fmt.Println(len(k)) // 2
}
```

La cheile de tip interfață, două valori sunt aceeași cheie doar dacă au **același tip dinamic** și valori egale. O cheie al cărei tip dinamic nu e comparabil (slice, map, funcție) dă panic la inserare sau căutare (vezi [Interfețe](../../interfete/3/)).

## Pe scurt

- Map-ul `nil` se poate citi, dar scrierea cere `make`: nu are unde pune cheia.
- `&m[k]` e interzis pentru că elementele se mută la creștere.
- Ordinea aleatoare previne dependențele ascunse și a permis schimbarea implementării.
- La iterare, cheile existente apar o dată; cele adăugate pe parcurs pot apărea sau nu.
- Cheile `float` urmează `==`: `-0` e `+0`, iar `NaN` nu poate fi găsit; `clear` e singura cale de a-l scoate.
