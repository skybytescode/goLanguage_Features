# Maps — Expert

Din Go 1.24, map-urile sunt implementate ca **Swiss tables**. Vedem structura lor, cum cresc, de ce memoria nu se întoarce după `delete`, cum e calculat hash-ul și cum detectează runtime-ul accesul concurent.

## De la buckets la Swiss tables

Până la Go 1.23, un map era un array de **buckets** de câte 8 perechi, cu buckets de overflow înlănțuite și un factor de încărcare de 6,5. Creșterea dubla array-ul și muta elementele treptat, la fiecare scriere ulterioară („evacuare incrementală”).

Go 1.24 a înlocuit implementarea (pachetul `internal/runtime/maps`) cu un design inspirat din Abseil:

```go,ignore
// simplificat
type Map struct {
	used      uint64
	seed      uintptr  // sămânța aleatoare a hash-ului, per map
	directory []*table // extendible hashing
	// ...
}

type table struct {
	groups   groupsReference // grupuri de câte 8 sloturi
	capacity uint16          // cel mult 1024 de sloturi
	// ...
}

// un grup: un cuvânt de control (8 octeți) + 8 sloturi cheie/valoare
// fiecare octet de control: liber / șters / ocupat + 7 biți din hash (H2)
```

La o căutare, hash-ul de 64 de biți se împarte în:

- **H1** (57 de biți): alege grupul de start; sondarea continuă **pătratic** între grupuri;
- **H2** (7 biți): comparat cu toți cei 8 octeți de control **dintr-o singură operație** (SIMD pe amd64, operații pe biți în rest).

Doar sloturile al căror H2 se potrivește sunt comparate efectiv cu cheia. Rezultatul: mai puține accese la memorie, factor de încărcare mai mare (7/8) și, în benchmark-urile Go, operații cu 20–60% mai rapide pe map-uri mari.

Map-urile **mici** (cel mult 8 elemente) sunt un singur grup, fără tabel și fără director.

## Creșterea: limitată per tabel

Un tabel are cel mult 1024 de sloturi. Când unul se umple peste 7/8, e **dublat** dacă e sub limită, altfel e **împărțit** în două, iar directorul (extendible hashing) se dublează la nevoie. O creștere atinge deci cel mult 1024 de sloturi odată, ceea ce ține sub control latența unei inserări, fără mecanismul de evacuare incrementală al vechii implementări.

Sloturile șterse devin **tombstones** (marcaj „șters”), ca sondarea să nu se oprească prematur; ele sunt reutilizate la inserări și curățate la următoarea creștere.

## Memoria nu scade după `delete`

Un map **nu se micșorează niciodată**. Ștergerea tuturor cheilor păstrează tabelele alocate:

```go
package main

import (
	"fmt"
	"runtime"
)

func heapMiB() uint64 {
	runtime.GC()
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	return ms.HeapAlloc >> 20
}

func main() {
	m := make(map[int][64]byte)
	for i := range 500_000 {
		m[i] = [64]byte{}
	}
	fmt.Println("plin:", heapMiB(), "MiB")

	for k := range m {
		delete(m, k)
	}
	fmt.Println("după delete:", heapMiB(), "MiB, len =", len(m)) // aproape la fel

	m = nil
	fmt.Println("după m = nil:", heapMiB(), "MiB")
}
```

Pentru cache-uri care cresc temporar și apoi se golesc, recreează map-ul (`m = make(map[K]V)`) în loc să ștergi cheile. `clear(m)` are același comportament ca `delete` pe toate cheile: păstrează memoria.

## Chei și valori mari

Cheile și valorile mai mari de 128 de octeți nu sunt stocate direct în sloturi: slotul conține un pointer la o alocare separată. Pentru valori mari, un `map[K]*V` explicit poate fi mai eficient, dar adaugă presiune pe GC.

## Hash-ul

Fiecare map are o **sămânță aleatoare** (`seed`), aleasă la creare. Asta protejează împotriva atacurilor prin coliziuni (input construit ca toate cheile să ajungă în același loc) și e și motivul pentru care ordinea la `range` diferă între map-uri și între rulări. Pe procesoarele cu AES-NI, hash-ul pentru string-uri și octeți folosește instrucțiuni AES.

Costul hash-ului depinde de cheie: un `int` e ieftin, un `string` lung trebuie citit integral, iar o cheie interfață (`map[any]V`) cere întâi aflarea tipului dinamic. Pachetul `hash/maphash` (inclusiv `maphash.Comparable`, din Go 1.24) expune același algoritm pentru structuri de date proprii.

## Detectarea accesului concurent

Map-ul are un bit „se scrie acum”. O scriere îl setează la început și îl șterge la final; orice altă operație care îl găsește setat oprește programul cu `fatal error: concurrent map writes` sau `concurrent map read and map write`. Detecția e **oportunistă**: prinde doar suprapunerile care se întâmplă efectiv, deci absența erorii nu dovedește corectitudinea. `-race` face analiza completă.

Eroarea e fatală, nu panic, pentru că structura internă poate fi deja coruptă; continuarea ar putea produce rezultate greșite în tăcere.

## Pe scurt

- Go 1.24+: Swiss tables cu grupuri de 8 sloturi, octeți de control și sondare cu H1/H2.
- Creșterea e limitată la tabele de cel mult 1024 de sloturi.
- Map-urile nu se micșorează; recreează-le după goliri mari.
- Hash cu sămânță aleatoare per map; cheile și valorile peste 128 de octeți sunt indirecte.
- Detecția concurentă e oportunistă și fatală; folosește `-race`.
