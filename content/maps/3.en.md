# Maps — Advanced

The design decisions behind maps: why the zero value is readable but not writable, why you can't take an element's address, why order is random on purpose, and what the spec guarantees during iteration.

## The `nil` map: readable, but not writable

A map variable is a pointer to a runtime structure. The zero value is the `nil` pointer. Reading from a `nil` map is defined to behave like reading from an empty one (no memory is needed to answer "it doesn't exist"), but a write would need a structure to put the key in — and it has no way to create one, because it would have to modify the caller's **variable**, not just the structure. That's why writing panics and `make` is mandatory.

The same logic explains why a function receiving a map **can** add keys (it modifies the shared structure), but can't replace the caller's map with a new one.

## Why you can't take an element's address

`&m[k]` doesn't compile. The reason: when it grows, the map **moves** elements into new tables. A pointer taken earlier would point to old memory, and writes through it would be lost or, worse, corrupt other data. Unlike slices — where a pointer to an old element stays valid, just into a different array — here the runtime couldn't even guarantee memory safety.

The same reason is why `m[k].Field = x` doesn't compile: it would need the element's address.

## Random order is a design decision

In early versions, iteration order was stable "by accident", and programs started depending on it. When the implementation changed, the code broke. Go 1.0 made the order **intentionally random**: every `range` starts from a randomly chosen point. That way, any dependence on order shows up immediately in tests, not years later, on an implementation change. The switch to Swiss tables in Go 1.24 was possible precisely because nobody could depend on the old implementation's order.

```go
package main

import "fmt"

func main() {
	m := map[int]bool{1: true, 2: true, 3: true, 4: true, 5: true}
	for range 3 {
		for k := range m {
			fmt.Print(k, " ")
		}
		fmt.Println() // the order usually differs from one walk to the next
	}
}
```

## Iteration

The iterator starts at a random position and remembers the directory from the start. The spec only guarantees that:

- every key that exists for the whole iteration appears exactly once;
- a key deleted before it's reached won't appear;
- a key added during iteration may or may not appear.

The implementation keeps these guarantees even when tables grow or split during the walk.

## Surprising keys: `float` and interfaces

Key equality is `==`, with all of the type's quirks:

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	m := map[float64]string{}
	m[0.0] = "zero"
	m[math.Copysign(0, -1)] = "minus zero" // -0 == +0: the same key
	fmt.Println(len(m), m[0])              // 1 minus zero

	nan := math.NaN()
	m[nan] = "a"
	m[nan] = "b" // NaN != NaN: every insert creates a new key
	_, found := m[nan]
	fmt.Println(len(m), found) // 3 false: NaN keys can't be looked up or deleted with delete

	clear(m) // Go 1.21: the only way to get rid of NaN keys
	fmt.Println(len(m))

	k := map[any]int{}
	k[1] = 1
	k[int64(1)] = 2     // a different dynamic type: a different key
	fmt.Println(len(k)) // 2
}
```

With interface keys, two values are the same key only if they have **the same dynamic type** and equal values. A key whose dynamic type isn't comparable (slice, map, function) panics on insertion or lookup (see [Interfaces](../../interfete/3/)).

## Summary

- A `nil` map can be read, but writing needs `make`: there's nowhere to put the key.
- `&m[k]` is forbidden because elements move when the map grows.
- Random order prevents hidden dependencies and allowed the implementation to change.
- During iteration, existing keys appear once; keys added along the way may or may not.
- `float` keys follow `==`: `-0` is `+0`, and `NaN` can never be found; `clear` is the only way to remove it.
