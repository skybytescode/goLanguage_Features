# Pointers — Expert

Where variables live and how the runtime sees them: escape analysis, heap allocation, why a `uintptr` isn't a pointer, and the GC's write barriers.

## Escape analysis: stack or heap?

The Go spec doesn't talk about stack and heap. The compiler decides: a variable lives on the function's stack if it can prove it's **not used after the function returns**. Otherwise it "escapes" to the heap, where the GC will free it.

Stack allocations are practically free; heap allocations cost when allocating and, above all, later, at collection time. The decision is visible with `-gcflags=-m`:

```go,ignore
package main

type Point struct{ X, Y int }

func onStack() int {
	p := Point{1, 2} // doesn't escape: stays on the stack
	return p.X + p.Y
}

func onHeap() *Point {
	p := Point{1, 2} // moved to heap: p
	return &p
}

func viaInterface(v any) {}

func main() {
	x := 42
	viaInterface(x) // x escapes to heap (usually: the value is copied into an interface)
}
```

```bash
$ go build -gcflags='-m' .
./main.go:10:2: moved to heap: p
./main.go:18:15: x escapes to heap
```

Common causes of escape:

- returning a pointer to a local variable;
- storing a pointer in a global variable, a map, a channel or a field of a heap object;
- converting to an interface (e.g. arguments to `fmt.Println`), if the compiler can't prove the value isn't retained;
- closures that capture by reference and outlive the function;
- sizes unknown at compile time (`make([]byte, n)` with a variable `n`) or very large values.

The typical optimization in a hot loop: reuse a buffer instead of allocating a new one each iteration, or take the buffer from the caller (as `io.Reader.Read(p []byte)` does).

## `uintptr` is not a pointer

`uintptr` is an integer. The GC doesn't track it: if you store an object's address in a `uintptr`, the object may be collected or moved (stacks move when they grow). Conversions between `unsafe.Pointer` and `uintptr` are safe only in the precise patterns documented in the `unsafe` package; details in the [Reflection and unsafe](../../reflect-unsafe/4/) topic.

## Write barriers

Go's GC runs concurrently with the program. So it doesn't miss pointers moved while it's marking, the compiler inserts a **write barrier** whenever a pointer is written to heap memory while the GC is active. It's one reason why pointer-free structures (e.g. `[]int` vs `[]*int`) are cheaper for the GC: they don't need scanning and don't trigger barriers.

## What a heap allocation looks like

When escape analysis moves a variable to the heap, the compiler replaces the stack reservation with a call to the allocator. In the assembly (`go build -gcflags=-S`) you can see it directly:

```text
// p := &Point{1, 2}, when p escapes the function
LEAQ    type:main.Point(SB), AX   // the type descriptor
CALL    runtime.newobject(SB)     // allocation + zeroing, by size class
MOVQ    $1, (AX)
MOVQ    $2, 8(AX)
```

`runtime.newobject` receives the type descriptor because the allocator needs to know the size and whether the object contains pointers (a "scan" or "noscan" span, see [Runtime](../../runtime/4/)). A `make([]T, n)` that escapes becomes `runtime.makeslice`, and `new(T)` and `&T{}` become the same `newobject`. Each of these calls shows up in allocation profiles (`-memprofile`) with the source line that produced it.

## Summary

- Escape analysis picks stack or heap; check with `-gcflags=-m`.
- A variable that escapes becomes a `runtime.newobject` call with the type's descriptor.
- `uintptr` doesn't keep objects alive and isn't updated when stacks move.
- The write barrier is only active during marking; fewer pointers = less work for the GC.
