# Variables, types and constants — Expert

How the compiler and runtime handle variables and types: how constants are represented in the compiler, initialization order, memory layout, type descriptors in the binary and zero-size values.

## How the compiler represents constants

The "arbitrary" precision of constants isn't a figure of speech: the compiler uses the `go/constant` package, built on `math/big`. Integers are `big.Int`, and fractions are kept as **exact rational numbers** (`big.Rat`) whenever possible, with `big.Float` only as a fallback. You can use the same package directly:

```go
package main

import (
	"fmt"
	"go/constant"
	"go/token"
)

func main() {
	x := constant.Shift(constant.MakeInt64(1), token.SHL, 100) // 1 << 100
	fmt.Println(x, constant.BitLen(x))                         // 1267650600228229401496703205376 101

	third := constant.BinaryOp(constant.MakeInt64(1), token.QUO, constant.MakeInt64(3))
	back := constant.BinaryOp(third, token.MUL, constant.MakeInt64(3))
	fmt.Println(constant.Compare(back, token.EQL, constant.MakeInt64(1))) // true: exact arithmetic
}
```

The spec requires implementations to represent integer constants with at least 256 bits and floating-point constants with a mantissa of at least 256 bits; the `gc` compiler goes well beyond that. Only on **conversion** to a concrete type is the value checked and rounded — hence errors like `constant 300 overflows uint8`.

## Initialization order

Package-level variables are initialized **in dependency order**, not necessarily in source order. Only then do the `init()` functions run, in the order they appear (the `go` command hands files to the compiler sorted by name):

```go
package main

import "fmt"

var (
	a = b + 1 // depends on b, so b is initialized first
	b = f()
)

func f() int {
	fmt.Println("initializing b")
	return 41
}

func init() {
	fmt.Println("init: a =", a)
}

func main() {
	fmt.Println("main")
}
```

Imported packages are fully initialized before the package that imports them. Initialization cycles are compile errors.

## What values look like in memory

Values have a fixed size and alignment. Struct fields are aligned, and the compiler inserts *padding* between them, so field order matters:

```go
package main

import (
	"fmt"
	"unsafe"
)

type Wasteful struct {
	a bool  // 1 byte + 7 padding
	b int64 // 8
	c bool  // 1 byte + 7 padding
}

type Compact struct {
	b int64 // 8
	a bool  // 1
	c bool  // 1 + 6 padding
}

func main() {
	fmt.Println(unsafe.Sizeof(Wasteful{}), unsafe.Sizeof(Compact{})) // 24 16
	fmt.Println(unsafe.Sizeof(""), unsafe.Sizeof([]int{}))           // 16 24
}
```

A `string` is a 2-word header (pointer + length); a slice is 3 words (pointer, length, capacity). The `fieldalignment` analyzer (from `golang.org/x/tools`) suggests the optimal field order.

## Type descriptors in the binary

Every type used at run time (through interfaces, reflection, heap allocation) has a **descriptor** in the binary (`internal/abi.Type`), generated by the compiler:

```go,ignore
type Type struct {
	Size_       uintptr // size in bytes
	PtrBytes    uintptr // the prefix that may contain pointers (the rest isn't scanned by the GC)
	Hash        uint32  // the type's hash, used by type switches and maps
	TFlag       TFlag
	Align_      uint8
	FieldAlign_ uint8
	Kind_       Kind
	Equal       func(unsafe.Pointer, unsafe.Pointer) bool // nil if the type isn't comparable
	GCData      *byte // the pointer bitmap, for the GC
	Str         NameOff
	PtrToThis   TypeOff
}
```

`reflect.TypeOf(x)` returns exactly this descriptor, seen through the `reflect.Type` interface:

```go
package main

import (
	"fmt"
	"reflect"
)

type Point struct {
	X, Y int32
	Name string
}

func main() {
	t := reflect.TypeOf(Point{})
	fmt.Println(t.Size(), t.Align(), t.Kind(), t.Comparable()) // 24 8 struct true
	for i := range t.NumField() {
		f := t.Field(i)
		fmt.Printf("%-4s offset=%-2d size=%d\n", f.Name, f.Offset, f.Type.Size())
	}
}
```

`PtrBytes` and `GCData` explain why pointer-free structs are cheap for the GC: the GC reads the bitmap and skips everything that can't hold pointers. The `Equal` function is what `==` on interfaces and maps uses; for types with no padding and no special fields (floats, strings, interfaces), it boils down to a memory comparison (`memequal`).

## Zero-size values

Every zero-size allocation (`new(struct{})`, `make([]int, 0)` on the heap, `[0]int{}`) gets the same address: the global variable `runtime.zerobase`. Nothing is allocated. The consequence: the spec says explicitly that two pointers to distinct zero-size variables **may or may not** be equal.

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	a, b := new(struct{}), new(struct{})
	fmt.Println(unsafe.Sizeof(*a)) // 0
	fmt.Println(a == b)            // unspecified: don't rely on the result
}
```

That's why `struct{}` is ideal as a set value and as a channel signal: zero bytes, zero allocations.

## Summary

- The compiler computes constants exactly, with `go/constant` (on top of `math/big`).
- Package initialization follows dependencies, then `init()`.
- Field order changes struct size (padding, alignment).
- Every type has a descriptor in the binary: size, pointer bitmap, hash, equality function.
- Zero-size values don't allocate and may share the same address.
