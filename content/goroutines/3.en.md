# Goroutines — Advanced

What the language guarantees about goroutines (the memory model), who is responsible for a started goroutine, what one costs, and two settings that matter in production: `GOMAXPROCS` in containers and pinned threads.

## What the memory model guarantees

Go's memory model defines when a write in one goroutine is guaranteed to be visible in another. For goroutines, the rules are few:

- the `go f()` statement **happens before** `f` starts executing: everything the parent goroutine wrote before `go` is visible in `f`;
- a goroutine's exit is **not** synchronized with anything: without a channel, a `WaitGroup` or a mutex, nobody is guaranteed to see what it wrote.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	message := "prepared before go" // guaranteed visible in the goroutine
	var result string
	var wg sync.WaitGroup
	wg.Go(func() {
		result = message + ", processed"
	})
	wg.Wait() // Wait synchronizes: the write to result is visible after it
	fmt.Println(result)
}
```

Without `wg.Wait()`, reading `result` would be a data race: the program might see the old value, the new one, or — for multi-word types such as a string — a corrupted mix of the two.

## Who owns a goroutine

Go has no "structured concurrency" enforced by the language: a started goroutine lives independently of the function that started it. The discipline has to come from the code:

- the function that starts goroutines **waits** for them to finish before returning (`WaitGroup`, `errgroup`), or
- it hands them a way to stop (`context`) and documents who cancels it.

A useful rule: if you can't say **when and why** a goroutine stops, you have a potential leak. In tests, `goleak` (go.uber.org/goleak) or the `goroutine` profile find them.

## What a goroutine costs

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	var before, after runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&before)

	const n = 10_000
	var wg sync.WaitGroup
	stop := make(chan struct{})
	for range n {
		wg.Go(func() { <-stop }) // they all stay blocked until close
	}
	runtime.ReadMemStats(&after)
	fmt.Printf("~%d bytes of stack per goroutine\n", (after.StackInuse-before.StackInuse)/n)

	close(stop)
	wg.Wait()
}
```

An idle goroutine costs around 2–8 KiB of stack plus a `g` struct of a few hundred bytes. A million goroutines therefore means a few GB: cheap, but not free. Switching between goroutines costs hundreds of nanoseconds, versus microseconds for operating system threads.

## `GOMAXPROCS` in containers (Go 1.25)

The default used to be the machine's core count. In a container limited to 2 CPUs on a 64-core machine, that meant 64 Ps and severe throttling by the cgroup. Since Go 1.25, the runtime reads the CPU limit from the cgroup and adjusts `GOMAXPROCS` automatically, including when the limit changes at run time. Setting the `GOMAXPROCS` environment variable explicitly disables the adjustment.

## Pinned threads: `runtime.LockOSThread`

Some C libraries or system APIs (OpenGL, some Linux namespace calls) require calls to come from the **same** thread. `runtime.LockOSThread` binds the current G to its M until `UnlockOSThread`. If the goroutine exits without unlocking, the thread is destroyed, not reused.

## Summary

- `go f()` happens before the start; exit isn't synchronized without explicit primitives.
- Every goroutine needs an "owner" that waits for it or stops it.
- A goroutine costs a few KiB; a million cost a few GB.
- Since Go 1.25, `GOMAXPROCS` respects container CPU limits.
- `runtime.LockOSThread` for thread-bound APIs.
