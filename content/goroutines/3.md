# Goroutines — Avansat

Ce garantează limbajul despre goroutines (modelul de memorie), cine e responsabil de o goroutine pornită, cât costă una, și două setări care contează în producție: `GOMAXPROCS` în containere și firele blocate.

## Ce garantează modelul de memorie

Modelul de memorie Go definește când o scriere dintr-o goroutine e garantat vizibilă în alta. Pentru goroutines, regulile sunt puține:

- instrucțiunea `go f()` **se întâmplă înainte** de începerea execuției lui `f`: tot ce a scris goroutine-ul părinte înainte de `go` e vizibil în `f`;
- terminarea unei goroutine **nu** e sincronizată cu nimic: fără un channel, un `WaitGroup` sau un mutex, nimeni nu are garanția că vede ce a scris ea.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	mesaj := "pregătit înainte de go" // vizibil garantat în goroutine
	var rezultat string
	var wg sync.WaitGroup
	wg.Go(func() {
		rezultat = mesaj + ", procesat"
	})
	wg.Wait() // Wait sincronizează: scrierea lui rezultat e vizibilă după el
	fmt.Println(rezultat)
}
```

Fără `wg.Wait()`, citirea lui `rezultat` ar fi o cursă de date: programul ar putea vedea valoarea veche, cea nouă, sau — pentru tipuri de mai multe cuvinte, cum e un string — o combinație coruptă a celor două.

## Cine deține o goroutine

Go nu are „concurență structurată” impusă de limbaj: o goroutine pornită trăiește independent de funcția care a pornit-o. Disciplina trebuie impusă de cod:

- funcția care pornește goroutines **așteaptă** terminarea lor înainte să se întoarcă (`WaitGroup`, `errgroup`), sau
- le transmite un mijloc de oprire (`context`) și documentează cine îl anulează.

O regulă utilă: dacă nu poți spune **când și de ce** se oprește o goroutine, ai o scurgere potențială. În teste, `goleak` (go.uber.org/goleak) sau profilul `goroutine` le găsesc.

## Cât costă o goroutine

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	var inainte, dupa runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&inainte)

	const n = 10_000
	var wg sync.WaitGroup
	stop := make(chan struct{})
	for range n {
		wg.Go(func() { <-stop }) // toate rămân blocate până la close
	}
	runtime.ReadMemStats(&dupa)
	fmt.Printf("~%d octeți de stivă per goroutine\n", (dupa.StackInuse-inainte.StackInuse)/n)

	close(stop)
	wg.Wait()
}
```

O goroutine inactivă costă în jur de 2–8 KiB de stivă plus o structură `g` de câteva sute de octeți. Un milion de goroutines înseamnă deci câțiva GB: ieftine, dar nu gratuite. Comutarea între goroutines costă sute de nanosecunde, față de microsecunde pentru firele sistemului de operare.

## `GOMAXPROCS` în containere (Go 1.25)

Valoarea implicită era numărul de nuclee ale mașinii. Într-un container limitat la 2 CPU pe o mașină cu 64 de nuclee, asta însemna 64 de P-uri și throttling sever din partea cgroup-ului. Din Go 1.25, runtime-ul citește limita de CPU din cgroup și ajustează `GOMAXPROCS` automat, inclusiv dacă limita se schimbă în timpul rulării. Setarea explicită a variabilei de mediu `GOMAXPROCS` dezactivează ajustarea.

## Firul blocat: `runtime.LockOSThread`

Unele biblioteci C sau API-uri de sistem (OpenGL, unele apeluri Linux pe namespace-uri) cer ca apelurile să vină de pe **același** fir. `runtime.LockOSThread` leagă G-ul curent de M-ul lui până la `UnlockOSThread`. Dacă goroutine-ul se termină fără unlock, firul e distrus, nu refolosit.

## Pe scurt

- `go f()` se întâmplă înainte de start; terminarea nu e sincronizată fără primitive explicite.
- Fiecare goroutine are nevoie de un „proprietar” care o așteaptă sau o oprește.
- O goroutine costă câțiva KiB; un milion costă câțiva GB.
- Din Go 1.25, `GOMAXPROCS` respectă limitele de CPU ale containerului.
- `runtime.LockOSThread` pentru API-uri legate de fir.
