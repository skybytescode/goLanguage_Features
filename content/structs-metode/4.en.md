# Structs and methods — Expert

What the compiler generates for structs and methods: wrappers for promoted methods, equality functions, copying and zeroing memory, and when copying a struct becomes expensive.

## Promoted methods = generated wrappers

For every promoted method, the compiler generates a "wrapper" function on the outer type that computes the address of the embedded field and calls the real method. Wrappers show up in stack traces as `<autogenerated>`. If you embed a **pointer** (`*Address`), the wrapper dereferences it, so a `nil` embedded pointer panics on call.

Method sets with embedding:

| You embed | `S` gets | `*S` gets |
|---|---|---|
| `T` | methods of `T` | methods of `T` and `*T` |
| `*T` | methods of `T` and `*T` | methods of `T` and `*T` |

## The cost of copying

Structs are copied on assignment, when passed as arguments and in `range`. For large structs (hundreds of bytes), pointer receivers and `for i := range s` avoid repeated copies. For small structs (a few words), a value is usually **faster**: it sits in registers, needs no dereference and doesn't escape to the heap.

## Equality: generated functions

`a == b` on two structs isn't magic: the compiler generates an equality function per type (the `type:.eq.main.T` symbols in the binary), also used by maps and by interface comparison.

- If the struct has no padding and contains only types compared "bitwise" (integers, pointers, booleans), equality becomes a single `memequal` over the whole memory.
- `float` fields (where `+0 == -0` and `NaN != NaN`), strings (length, then content) and interfaces (type, then the type's `Equal`) need separate comparisons.
- Padding is **not** compared: its content is undefined, which is why the compiler can't use `memequal` on structs with "holes".

So field order matters twice: for size and for the cost of comparison.

## Copying and zeroing

Assigning a struct is a memory copy. The compiler picks the implementation by size:

| Size | Generated code (amd64) |
|---|---|
| a few words | inline `MOVQ`/`MOVUPS` instructions, sometimes just registers |
| tens to hundreds of bytes | unrolled SIMD instruction sequences or short loops (historically via "Duff's device": `DUFFCOPY`/`DUFFZERO`) |
| large | a call to `runtime.memmove` / `memclrNoHeapPointers` |

If the struct contains pointers and the destination is on the heap, the copy must also go through the write barrier while the GC is marking (`typedmemmove`), which makes it more expensive than copying pointer-free data.

## Embedded fields in memory

Embedding isn't a special run-time mechanism: an embedded field is an **ordinary**, unnamed field, laid out in the struct like any other. Promoted fields are just syntactic shorthand for an offset:

```go
package main

import (
	"fmt"
	"unsafe"
)

type Address struct {
	City, Street string
}

type Customer struct {
	ID      int64
	Address // embedded by value: 32 bytes inside Customer
	Active  bool
}

type CustomerPtr struct {
	ID       int64
	*Address // embedded by pointer: 8 bytes and a dereference on access
}

func main() {
	var c Customer
	fmt.Println(unsafe.Offsetof(c.Address), unsafe.Offsetof(c.City), unsafe.Offsetof(c.Street)) // 8 8 24
	fmt.Println(unsafe.Sizeof(c), unsafe.Sizeof(CustomerPtr{}))                                 // 48 16
}
```

`c.City` compiles exactly like `c.Address.City`: a base address plus offset 8, with no call or lookup. With a field embedded by **pointer**, access needs an extra dereference (and panics if the pointer is `nil`), and the outer struct no longer contains the data, only its address.

## Summary

- Promoted methods are compiler-generated wrappers (`<autogenerated>`).
- `==` on structs uses generated equality functions; without padding it becomes `memequal`.
- Copying picks inline instructions, SIMD sequences or `memmove` by size.
- Small structs copy practically for free; large ones deserve pointers or indexed `range`.
- An embedded field is an ordinary field; accessing promoted fields is a plain offset.
