# Packages and modules — Expert

What happens on disk and in the toolchain: the module cache, the package as the unit of compilation, export data, the linker and dead-code elimination, and the restrictions on `//go:linkname`.

## The module cache

Downloaded modules live in `$(go env GOMODCACHE)` (by default `~/go/pkg/mod`), **read-only**, one directory per version:

```text
~/go/pkg/mod/
├── cache/download/github.com/google/uuid/@v/
│   ├── v1.6.0.zip      ← the archive, exactly as it came from the proxy
│   ├── v1.6.0.mod
│   └── v1.6.0.ziphash  ← the hash checked against go.sum
└── github.com/google/uuid@v1.6.0/   ← the unpacked sources
```

Uppercase letters in paths are encoded with `!` (`github.com/!burnt!sushi/toml`), so it works on case-insensitive file systems too. The files are read-only so nobody accidentally edits a dependency "in place"; that's what `replace` and `go work` are for. `go clean -modcache` removes everything (the files are read-only, so a plain `rm -rf` fails).

For offline builds: `go mod download` fills the cache ahead of time, `GOPROXY=off` forbids downloads (the build fails if anything is missing from the cache), and `go mod vendor` copies the dependencies into the project.

## The unit of compilation: the package

The compiler (`go tool compile`) receives **all of a package's files** at once and produces an object file with **export data**: the types, the inlinable functions and the escape information of the exported API. Packages importing it read only that data, not the sources. Hence:

- packages compile in parallel, in the topological order of imports;
- import cycles are impossible by construction;
- a function from another package can be inlined (its body is in the export data).

Results are kept in the **build cache** (`go env GOCACHE`), keyed by the hash of every input (sources, flags, toolchain version, dependencies). A repeated build with no changes recompiles nothing; `go clean -cache` empties it.

## The linker and dead code

The linker starts from `main.main` and the `init` functions and includes only **reachable** symbols. Unused functions disappear from the binary. Exceptions that keep code alive:

- when the program uses `reflect.Value.Method`/`MethodByName` with names unknown at compile time, the linker must keep **every** exported method of every reachable type (that's why `text/template` can bloat binaries);
- `init` functions and the globals they initialize.

```bash
go build -ldflags='-s -w'   # no symbol table and no DWARF: a smaller binary
go version -m ./app         # the modules and versions embedded in the binary
```

## `//go:linkname`

The directive allows access to unexported symbols from another package (for example the runtime). Many popular libraries used it, blocking internal runtime changes. Since Go 1.23, the linker **rejects** `linkname` references to standard library symbols that aren't explicitly marked as allowed (`-checklinkname=0` disables the check temporarily). The message is clear: don't build on runtime internals.

## How the `go` command resolves an import

For `import "github.com/ana/shop/internal/stock"`, the `go` command:

1. checks whether it's a standard library package (paths with no dot in the first element, looked up in `GOROOT`);
2. otherwise, looks in the **build list** (the result of MVS) for the module with the **longest prefix** matching the path: `github.com/ana/shop`, not `github.com/ana`;
3. the rest of the path (`internal/stock`) is the directory inside the module;
4. the source comes from the main module's directory, from the workspace (`go.work`), from `vendor/` (if present and the `go` version ≥ 1.14 enables it), or from the module cache.

If no module in the list has a matching prefix, the error is `no required module provides package ...`, and `go get` (or `go mod tidy`) adds the module. Two modules that could provide the same package (for example `example.com/a` and `example.com/a/b`, both with a `b` directory) cause an `ambiguous import` error.

`go list -m all` prints the build list, and `go list -f '{{.Dir}}' package` shows exactly which directory a package comes from.

## Summary

- The module cache is read-only, with archives and hashes checked against `go.sum`.
- The package is the unit of compilation; export data enables cross-package inlining.
- The build cache is keyed by the hash of every input.
- The linker drops unreachable code; reflection on methods by name prevents it.
- `linkname` into the standard library's internals is restricted since Go 1.23.
- An import is resolved through the longest module prefix in the build list.
