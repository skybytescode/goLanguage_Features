# Pachete și module — Practician

Organizarea unui proiect real: pachetele `internal`, versiunile semantice și sufixul `/v2`, `replace`, workspace-urile, directiva `tool`, funcțiile `init` și convențiile de denumire.

## Pachetele `internal`

Un pachet aflat sub un director numit `internal` poate fi importat **doar** de cod din directorul părinte al lui `internal` (și din subdirectoarele acestuia). Compilatorul impune regula:

```text
github.com/ana/magazin/
├── go.mod
├── cmd/
│   └── server/main.go          // poate importa internal/...
├── internal/
│   ├── stoc/stoc.go            // privat modulului magazin
│   └── plati/plati.go
└── api/api.go                  // pachet public, poate fi importat de oricine
```

Un alt modul care încearcă `import "github.com/ana/magazin/internal/stoc"` primește o eroare de compilare. `internal` e modul principal de a-ți păstra libertatea de a schimba codul fără să strici utilizatorii.

## Structura `cmd/`

Un modul cu mai multe executabile le pune pe fiecare în `cmd/<nume>/`, fiecare cu propriul `package main`:

```bash
go build ./cmd/server
go install github.com/ana/magazin/cmd/import@latest
```

Nu există o structură „oficială” impusă; pentru proiecte mici, un singur pachet `main` la rădăcină e perfect.

## Versiuni semantice

Versiunile modulelor sunt tag-uri git de forma `vMAJOR.MINOR.PATCH`:

- **PATCH** (`v1.4.2` → `v1.4.3`): corecturi, fără schimbări de API;
- **MINOR** (`v1.4.3` → `v1.5.0`): funcționalități noi, compatibile;
- **MAJOR** (`v1` → `v2`): schimbări incompatibile.

`v0.x.y` nu promite nimic despre compatibilitate.

## Sufixul `/v2`

Regula de import compatibil: **dacă două pachete au aceeași cale de import, trebuie să fie compatibile**. De aceea, o versiune majoră nouă (≥ 2) are o cale diferită:

```text
module github.com/ana/magazin/v2
```

```go,ignore
import (
	magazin "github.com/ana/magazin"      // v1
	magazinv2 "github.com/ana/magazin/v2" // v2, poate coexista în același program
)
```

Așa un program poate folosi simultan v1 (printr-o dependență veche) și v2, fără conflict. `math/rand/v2` din biblioteca standard urmează exact această regulă.

## `go get` și actualizări

```bash
go get example.com/lib@v1.5.0     # o versiune anume
go get example.com/lib@latest     # cea mai nouă
go get -u ./...                   # actualizează toate dependențele (minor/patch)
go get example.com/lib@none       # elimină dependența
go list -m -u all                 # ce actualizări sunt disponibile
```

## `replace`: dezvoltare locală

Când lucrezi simultan la o aplicație și la o bibliotecă, poți indica o copie locală:

```text
module github.com/ana/aplicatie

go 1.26

require github.com/ana/biblioteca v1.2.0

replace github.com/ana/biblioteca => ../biblioteca
```

`replace` are efect **doar** în modulul principal (cel pe care îl compilezi); e ignorat când modulul tău e o dependență a altcuiva. Nu uita să-l scoți înainte de publicare.

## Workspace-uri: `go.work`

Pentru mai multe module dezvoltate împreună, un workspace evită `replace`-urile temporare:

```bash
go work init ./aplicatie ./biblioteca
```

```text
go 1.26

use (
	./aplicatie
	./biblioteca
)
```

`go.work` e de obicei **local** (nu se pune în git), pentru că descrie configurația ta de dezvoltare. Cu `GOWORK=off` îl dezactivezi temporar.

## Unelte ca dependențe: directiva `tool` (Go 1.24)

Uneltele de dezvoltare (generatoare de cod, linters) se pot declara în `go.mod`, cu versiunea fixată ca orice dependență:

```bash
go get -tool golang.org/x/tools/cmd/stringer
go tool stringer -type=Stare
```

```text
tool golang.org/x/tools/cmd/stringer
```

Înlocuiește vechiul truc cu fișierul `tools.go` și importuri goale.

## Funcțiile `init`

Fiecare fișier poate avea oricâte funcții `init()`, rulate automat la inițializarea pachetului, după variabilele globale:

```go
package main

import "fmt"

var tabel = map[string]int{}

func init() {
	tabel["unu"] = 1 // pregătire care nu încape într-o expresie
}

func main() {
	fmt.Println(tabel)
}
```

Folosește-le cu măsură: rulează la import, ascund efecte secundare și fac testarea mai grea. Un tipar legitim: înregistrarea în registre globale (`database/sql` drivers, `image` formats), activată cu un import gol:

```go,ignore
import _ "github.com/lib/pq" // rulează doar init(), care înregistrează driverul "postgres"
```

## Denumirea pachetelor

- Nume scurte, cu litere mici, un singur cuvânt: `http`, `json`, `stoc`. Fără `_` sau majuscule.
- Evită `util`, `common`, `helpers`: nu spun nimic despre conținut.
- Nu repeta numele pachetului în identificatori: `stoc.Produs`, nu `stoc.StocProdus`. Apelantul scrie mereu numele pachetului.
- Numele directorului și numele pachetului ar trebui să coincidă.

## Importurile ciclice sunt interzise

Dacă pachetul `a` importă `b`, atunci `b` nu poate importa `a`, direct sau indirect. Ciclurile se rup de obicei mutând tipurile comune într-un al treilea pachet, sau definind o interfață în pachetul care consumă (vezi [Interfețe](../../interfete/2/)).

## Pe scurt

- `internal/` ascunde pachete de restul lumii.
- Versiunile majore ≥ 2 schimbă calea modulului (`/v2`).
- `replace` și `go.work` pentru dezvoltare locală pe mai multe module.
- `tool` în `go.mod` fixează versiunile uneltelor.
- `init` rar; pachete cu nume scurte și fără cicluri.
