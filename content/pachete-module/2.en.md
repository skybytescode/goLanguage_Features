# Packages and modules — Practitioner

Organizing a real project: `internal` packages, semantic versions and the `/v2` suffix, `replace`, workspaces, the `tool` directive, `init` functions and naming conventions.

## `internal` packages

A package under a directory named `internal` can be imported **only** by code in the directory that contains `internal` (and its subdirectories). The compiler enforces the rule:

```text
github.com/ana/shop/
├── go.mod
├── cmd/
│   └── server/main.go          // may import internal/...
├── internal/
│   ├── stock/stock.go          // private to the shop module
│   └── payments/payments.go
└── api/api.go                  // a public package anyone can import
```

Another module trying `import "github.com/ana/shop/internal/stock"` gets a compile error. `internal` is the main way to keep the freedom to change code without breaking users.

## The `cmd/` layout

A module with several executables puts each in `cmd/<name>/`, each with its own `package main`:

```bash
go build ./cmd/server
go install github.com/ana/shop/cmd/import@latest
```

There's no "official" layout you must follow; for small projects, a single `main` package at the root is perfectly fine.

## Semantic versions

Module versions are git tags of the form `vMAJOR.MINOR.PATCH`:

- **PATCH** (`v1.4.2` → `v1.4.3`): fixes, no API changes;
- **MINOR** (`v1.4.3` → `v1.5.0`): new, compatible features;
- **MAJOR** (`v1` → `v2`): incompatible changes.

`v0.x.y` promises nothing about compatibility.

## The `/v2` suffix

The import compatibility rule: **if two packages have the same import path, they must be compatible**. That's why a new major version (≥ 2) has a different path:

```text
module github.com/ana/shop/v2
```

```go,ignore
import (
	shop "github.com/ana/shop"      // v1
	shopv2 "github.com/ana/shop/v2" // v2, can coexist in the same program
)
```

So a program can use v1 (through an old dependency) and v2 at the same time, without conflict. The standard library's `math/rand/v2` follows exactly this rule.

## `go get` and upgrades

```bash
go get example.com/lib@v1.5.0     # a specific version
go get example.com/lib@latest     # the newest
go get -u ./...                   # upgrade every dependency (minor/patch)
go get example.com/lib@none       # remove the dependency
go list -m -u all                 # which upgrades are available
```

## `replace`: local development

When you work on an application and a library at the same time, you can point to a local copy:

```text
module github.com/ana/app

go 1.26

require github.com/ana/library v1.2.0

replace github.com/ana/library => ../library
```

`replace` applies **only** in the main module (the one you're building); it's ignored when your module is someone else's dependency. Remember to remove it before publishing.

## Workspaces: `go.work`

For several modules developed together, a workspace avoids temporary `replace`s:

```bash
go work init ./app ./library
```

```text
go 1.26

use (
	./app
	./library
)
```

`go.work` is usually **local** (not committed), since it describes your development setup. `GOWORK=off` disables it temporarily.

## Tools as dependencies: the `tool` directive (Go 1.24)

Development tools (code generators, linters) can be declared in `go.mod`, with their version pinned like any dependency:

```bash
go get -tool golang.org/x/tools/cmd/stringer
go tool stringer -type=State
```

```text
tool golang.org/x/tools/cmd/stringer
```

It replaces the old trick with a `tools.go` file and blank imports.

## `init` functions

Each file can have any number of `init()` functions, run automatically at package initialization, after the global variables:

```go
package main

import "fmt"

var table = map[string]int{}

func init() {
	table["one"] = 1 // setup that doesn't fit in an expression
}

func main() {
	fmt.Println(table)
}
```

Use them sparingly: they run on import, hide side effects and make testing harder. A legitimate pattern: registering in global registries (`database/sql` drivers, `image` formats), triggered by a blank import:

```go,ignore
import _ "github.com/lib/pq" // runs only init(), which registers the "postgres" driver
```

## Naming packages

- Short, lowercase, single-word names: `http`, `json`, `stock`. No `_` or capitals.
- Avoid `util`, `common`, `helpers`: they say nothing about the contents.
- Don't repeat the package name in identifiers: `stock.Product`, not `stock.StockProduct`. The caller always writes the package name.
- The directory name and the package name should match.

## Import cycles are forbidden

If package `a` imports `b`, then `b` can't import `a`, directly or indirectly. Cycles are usually broken by moving shared types into a third package, or by defining an interface in the consuming package (see [Interfaces](../../interfete/2/)).

## Summary

- `internal/` hides packages from the rest of the world.
- Major versions ≥ 2 change the module path (`/v2`).
- `replace` and `go.work` for local development across modules.
- `tool` in `go.mod` pins tool versions.
- Rare `init`; short package names and no cycles.
