# Tooling și profiling — Avansat

Uneltele care schimbă cum construiești și livrezi: optimizarea ghidată de profil (PGO), binarele statice și reproductibile, și depanarea cu Delve.

## PGO: optimizare ghidată de profil (Go 1.21)

Compilatorul poate folosi un profil CPU din producție ca să decidă unde merită optimizări agresive:

```bash
# 1. colectezi un profil reprezentativ din producție
curl -o default.pgo 'http://serviciu:6060/debug/pprof/profile?seconds=60'
# 2. îl pui lângă pachetul main, ca default.pgo, și îl adaugi în git
mv default.pgo ./cmd/server/
# 3. build-ul îl folosește automat (-pgo=auto e implicit)
go build ./cmd/server
```

Ce face cu el: mărește bugetul de **inlining** pentru apelurile fierbinți și **devirtualizează** apelurile prin interfețe când profilul arată un tip concret dominant. Câștigul tipic anunțat de echipa Go: 2–14% CPU. Procesul e iterativ și stabil: un profil luat dintr-un binar construit cu PGO e în continuare valid pentru build-ul următor.

## Binare statice și reproductibile

```bash
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w -buildid=' -o app ./cmd/app
```

- **`CGO_ENABLED=0`**: binar complet static, fără dependență de libc; rulează într-o imagine `scratch` sau `distroless`. (Pachetele `net` și `os/user` au implementări pure Go folosite atunci.)
- **`-trimpath`**: elimină căile absolute de pe mașina de build din binar.
- **`-s -w`**: fără tabela de simboluri și informații DWARF (binar mai mic, dar fără depanare).

Toolchain-ul Go e **reproductibil** din Go 1.21: aceleași surse, aceeași versiune și aceleași flag-uri produc un binar identic bit cu bit, pe orice mașină. Chiar binarele oficiale ale Go pot fi verificate astfel.

## Depanare: Delve

`dlv` (github.com/go-delve/delve) e debugger-ul care înțelege goroutines, interfețe și runtime-ul Go:

```bash
dlv debug ./cmd/server -- --port=8080
(dlv) break server.go:42
(dlv) continue
(dlv) goroutines              # toate goroutines, cu locația curentă
(dlv) goroutine 17 stack
(dlv) print cerere.Header
dlv attach <pid>              # la un proces care rulează
dlv core ./app core.1234      # post-mortem, pe un core dump (GOTRACEBACK=crash)
```

Optimizările îngreunează depanarea (variabile eliminate, funcții inlined); `-gcflags='all=-N -l'` le dezactivează. `dlv debug` face asta automat.

## Cross-compilare și cgo

Cross-compilarea Go „pur” nu cere nimic în plus: `GOOS=linux GOARCH=arm64 go build`. Situația se schimbă când apare **cgo** (cod C apelat din Go, sau dependențe care îl folosesc, ca unele drivere SQLite):

- la cross-compilare, `CGO_ENABLED` devine implicit `0`; pachetele care cer cgo nu se mai compilează;
- pentru a-l păstra ai nevoie de un compilator C pentru platforma țintă (`CC=aarch64-linux-gnu-gcc`, sau `zig cc` ca cross-compiler universal);
- binarul cu cgo depinde dinamic de libc, deci nu mai rulează într-o imagine `scratch`.

Pachetele din biblioteca standard care au variante cu și fără cgo (`net` pentru rezolvarea DNS, `os/user`) aleg automat implementarea pură Go când cgo e dezactivat. Poți forța alegerea și cu cgo activ: `-tags netgo,osusergo`.

```bash
go env CGO_ENABLED                             # 1 local, de obicei
GOOS=windows go env CGO_ENABLED                # 0 la cross-compilare
CGO_ENABLED=1 CC="zig cc -target aarch64-linux-gnu" GOOS=linux GOARCH=arm64 go build
```

## Pe scurt

- PGO: `default.pgo` lângă `main` → inlining și devirtualizare ghidate de producție.
- `CGO_ENABLED=0 -trimpath` pentru binare statice; build-urile Go sunt reproductibile.
- Delve înțelege goroutines; `dlv core` pentru analiză post-mortem.
- Cross-compilarea dezactivează implicit cgo; pentru a-l păstra ai nevoie de un compilator C pentru țintă.
