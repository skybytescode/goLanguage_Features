# Tooling and profiling — Practitioner

Profiling with `pprof` (CPU, heap, goroutines, blocking, mutex), profiling services in production with `net/http/pprof`, the execution trace, `go generate`, version information in the binary, and `go fix`.

## The profile types

| Profile | What it shows | How to get it |
|---|---|---|
| **CPU** | where processor time goes (sampling at 100 Hz) | `-cpuprofile`, `pprof.StartCPUProfile` |
| **heap** | memory in use now (`inuse`) and total allocated (`alloc`) | `-memprofile`, `pprof.WriteHeapProfile` |
| **allocs** | like heap, but defaulting to total allocations | `/debug/pprof/allocs` |
| **goroutine** | the stacks of every goroutine | `/debug/pprof/goroutine` |
| **block** | where goroutines sit blocked (channels, select) | `runtime.SetBlockProfileRate` |
| **mutex** | where goroutines wait on mutexes | `runtime.SetMutexProfileFraction` |

## A profile from code

```go
package main

import (
	"fmt"
	"os"
	"path/filepath"
	"runtime/pprof"
	"strings"
)

func heavyWork() int {
	total := 0
	for i := range 200_000 {
		total += len(strings.Repeat("x", i%100))
	}
	return total
}

func main() {
	path := filepath.Join(os.TempDir(), "cpu.out")
	f, err := os.Create(path)
	if err != nil {
		fmt.Println(err)
		return
	}
	defer os.Remove(path)

	pprof.StartCPUProfile(f)
	result := heavyWork()
	pprof.StopCPUProfile()
	f.Close()

	info, _ := os.Stat(path)
	fmt.Println("result:", result, "| profile written:", info.Size() > 0)
	// then: go tool pprof -http=:8080 cpu.out
}
```

## Reading a profile

```bash
go tool pprof -http=:8080 cpu.out    # web UI: flame graph, graph, source
go tool pprof cpu.out                # interactive in the terminal
(pprof) top 10                       # the functions with the most self time
(pprof) top -cum                     # by cumulative time (including callees)
(pprof) list heavyWork               # the source, with time per line
```

- **flat**: time spent in the function itself;
- **cum**: time in the function **and** everything it calls.

In a flame graph, width is time; look for wide "plateaus" at the top (where time is actually spent), not tall towers.

For memory, `-sample_index=alloc_space` shows who **allocates** a lot (GC pressure), and `inuse_space` who **holds** memory right now (leaks).

## Profiling in production: `net/http/pprof`

```go,ignore
import _ "net/http/pprof" // registers /debug/pprof/* on http.DefaultServeMux

func main() {
	go func() {
		// ONLY on an internal interface, never exposed publicly
		log.Println(http.ListenAndServe("localhost:6060", nil))
	}()
	// ... the application ...
}
```

```bash
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30   # CPU, 30 s
go tool pprof http://localhost:6060/debug/pprof/heap
curl http://localhost:6060/debug/pprof/goroutine?debug=2             # every stack
```

The CPU profile is cheap (a few percent) while running, so it can be collected in production. The goroutine profile is the first tool for goroutine leaks and deadlocks.

## The execution trace

Profiles aggregate; the **trace** shows what happened **over time**: which P each goroutine ran on, blocking, the GC, system calls.

```bash
go test -trace=trace.out ./...
go tool trace trace.out
curl -o trace.out http://localhost:6060/debug/pprof/trace?seconds=5
```

It's the right tool for latency (why did a request take 200 ms when the CPU was idle?), not for throughput.

## `go generate`

`go generate` runs commands written in special comments. It doesn't run automatically on build: it's an explicit step, and the result (the generated code) is committed.

```go,ignore
//go:generate go tool stringer -type=State
//go:generate protoc --go_out=. api.proto

type State int
```

```bash
go generate ./...
```

Generated files conventionally start with a `// Code generated ... DO NOT EDIT.` comment, which tools (linters, `gopls`, GitHub) recognize.

## The version in the binary

The `go` command automatically embeds build information: modules, versions, the git revision (`vcs.revision`), whether the tree was modified:

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	info, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Println("no build information")
		return
	}
	fmt.Println("Go version:", info.GoVersion)
	fmt.Println("module:", info.Main.Path, info.Main.Version)
	for _, s := range info.Settings {
		if s.Key == "vcs.revision" || s.Key == "GOOS" || s.Key == "GOARCH" {
			fmt.Println(s.Key, "=", s.Value)
		}
	}
}
```

For your own values, `-ldflags "-X main.version=v1.2.3"` sets a string variable at link time.

```bash
go version -m ./app     # the same information, read from an existing binary
```

## `go fix` and modernization (Go 1.26)

Since Go 1.26, `go fix` runs a set of **modernizers**: analyzers that automatically rewrite old patterns into today's idiomatic form — for example `for i := 0; i < n; i++` loops → `for i := range n`, `interface{}` → `any`, hand-written search loops → `slices.Contains`, `sort.Slice` → `slices.Sort`, needless `i := i` in loops.

```bash
go fix -diff ./...   # see what would change
go fix ./...         # apply
```

## Summary

- Six profiles: CPU, heap, allocs, goroutine, block, mutex.
- `go tool pprof -http` + `top`, `list`, flame graph; `flat` vs. `cum`.
- `net/http/pprof` on an internal interface for production.
- The trace for latency and behavior over time.
- `go generate` is explicit; `debug.ReadBuildInfo` for the version; `go fix` modernizes code.
