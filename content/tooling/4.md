# Tooling și profiling — Expert

Ce poți vedea în interiorul compilatorului (`-m`, SSA, assembly), „flight recorder”-ul pentru trace-uri în producție și scrierea propriilor analizoare statice.

## În interiorul compilatorului

```bash
go build -gcflags='-m' .        # inlining și escape analysis
go build -gcflags='-m=2' .      # cu motivele deciziilor
go build -gcflags='-S' . 2>asm.txt          # assembly-ul generat
go build -gcflags='-d=ssa/check_bce/debug=1' .  # verificările de limite rămase
GOSSAFUNC=NumeFunctie go build .            # ssa.html: fiecare pas al compilării SSA
go tool objdump -s 'main\.NumeFunctie' ./app    # dezasamblarea binarului final
```

`ssa.html` arată funcția după fiecare dintre cele ~50 de treceri ale back-end-ului SSA (eliminarea codului mort, propagarea constantelor, alocarea registrelor). E cea mai bună cale de a înțelege **de ce** o funcție nu e optimizată cum te așteptai.

Directivele de compilator relevante: `//go:noinline`, `//go:nosplit` (fără verificarea stivei în prolog; doar pentru runtime), `//go:noescape` (pentru funcții implementate în assembly), `//go:build`, `//go:embed`, `//go:generate`, `//go:debug`.

## Flight recorder (Go 1.25)

Un trace complet pe ore e imens. Problema: când apare un vârf de latență, e deja prea târziu să pornești trace-ul. `trace.FlightRecorder` ține **continuu** ultimele secunde de trace într-un buffer circular în memorie, iar tu îl salvezi doar când detectezi problema:

```go
package main

import (
	"bytes"
	"fmt"
	"runtime/trace"
	"time"
)

func main() {
	fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{
		MinAge:   2 * time.Second, // păstrează cel puțin ultimele 2 secunde
		MaxBytes: 16 << 20,
	})
	if err := fr.Start(); err != nil {
		fmt.Println(err)
		return
	}
	defer fr.Stop()

	start := time.Now()
	time.Sleep(30 * time.Millisecond) // „o cerere lentă”
	if time.Since(start) > 20*time.Millisecond {
		var buf bytes.Buffer
		if _, err := fr.WriteTo(&buf); err != nil { // salvează trace-ul recent
			fmt.Println(err)
			return
		}
		fmt.Println("trace salvat:", buf.Len() > 0)
		// în producție: scrii buf într-un fișier și îl analizezi cu go tool trace
	}
}
```

## Analizoare statice proprii

Framework-ul `golang.org/x/tools/go/analysis` e cel pe care sunt construite `go vet`, `gopls` și modernizatorii din `go fix`. Un analizor primește arborele sintactic **cu tipurile rezolvate** și raportează diagnostice, opțional cu fix-uri automate:

```go,ignore
var Analyzer = &analysis.Analyzer{
	Name: "nofmtprint",
	Doc:  "interzice fmt.Print* în pachetele de producție; folosiți log/slog",
	Run:  run,
}

func run(pass *analysis.Pass) (any, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}
			if fn, ok := typeutil.Callee(pass.TypesInfo, call).(*types.Func); ok &&
				fn.Pkg() != nil && fn.Pkg().Path() == "fmt" && strings.HasPrefix(fn.Name(), "Print") {
				pass.Reportf(call.Pos(), "fmt.%s în cod de producție", fn.Name())
			}
			return true
		})
	}
	return nil, nil
}
```

Rulat cu `singlechecker.Main(Analyzer)` ca unealtă de sine stătătoare, sau ca plugin în `golangci-lint`. Pentru verificări simple, `go vet -vettool=...` acceptă orice binar construit cu `unitchecker`.

## Pe scurt

- `-gcflags=-m`, `GOSSAFUNC`, `-S` și `objdump` arată ce a făcut compilatorul.
- `trace.FlightRecorder` (Go 1.25) salvează trace-ul doar când apare problema.
- `go/analysis` stă la baza lui `go vet`, `gopls` și `go fix`; îl poți folosi pentru reguli proprii.
