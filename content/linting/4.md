# Linting și golangci-lint — Expert

Cum funcționează `golangci-lint` pe dinăuntru: încărcarea pachetelor, framework-ul `go/analysis`, cache-ul, lanțul de procesare a alertelor și scrierea unui linter propriu, integrat ca plugin.

## Arhitectura unei rulări

```text
configurație ─► încărcare pachete (go/packages) ─► analizori (go/analysis) ─► procesoare ─► ieșire
                 AST + tipuri, o singură dată       toți linterii, în paralel    filtre, sortare   text/json/sarif
```

1. **Configurația**: `.golangci.yml`, flag-urile și valorile implicite stabilesc lista finală de linters și formatters.
2. **Încărcarea**: `golang.org/x/tools/go/packages` citește pachetele (cu `go list` dedesubt), le parsează și le verifică tipurile. Este cea mai scumpă etapă, așa că se face **o singură dată** pentru toți linterii.
3. **Analiza**: aproape toți linterii sunt `analysis.Analyzer`-i. `golangci-lint` îi grupează într-un singur „metalinter” (`goanalysis_metalinter`) care îi rulează în paralel, pe aceleași AST-uri și informații de tip.
4. **Procesarea**: alertele brute trec printr-un lanț de procesoare care filtrează, deduplică și sortează.
5. **Ieșirea**: unul sau mai multe formate, simultan.

De aceea `golangci-lint` e mult mai rapid decât rularea separată a 20 de unelte, fiecare cu propria încărcare a pachetelor.

## Framework-ul `go/analysis`

Un analizor e o valoare, nu un program:

```go,ignore
var Analyzer = &analysis.Analyzer{
	Name:     "nopanic",
	Doc:      "raportează apelurile panic din pachetele care nu sunt main",
	Requires: []*analysis.Analyzer{inspect.Analyzer}, // reutilizează rezultatul altui analizor
	Run:      run,
}

func run(pass *analysis.Pass) (any, error) {
	if pass.Pkg.Name() == "main" {
		return nil, nil
	}
	ins := pass.ResultOf[inspect.Analyzer].(*inspector.Inspector)
	ins.Preorder([]ast.Node{(*ast.CallExpr)(nil)}, func(n ast.Node) {
		call := n.(*ast.CallExpr)
		id, ok := call.Fun.(*ast.Ident)
		if !ok {
			return
		}
		// TypesInfo distinge built-in-ul panic de o funcție proprie numită panic
		if b, ok := pass.TypesInfo.Uses[id].(*types.Builtin); ok && b.Name() == "panic" {
			pass.Reportf(call.Pos(), "panic în pachetul de bibliotecă %s", pass.Pkg.Name())
		}
	})
	return nil, nil
}
```

Elementele importante ale lui `analysis.Pass`:

| Câmp | Ce oferă |
|---|---|
| `Files []*ast.File` | arborii sintactici ai pachetului |
| `TypesInfo *types.Info` | tipul fiecărei expresii, la ce obiect se referă fiecare identificator |
| `Pkg *types.Package` | pachetul curent, cu scope-ul lui |
| `ResultOf` | rezultatele analizorilor din `Requires` (de exemplu `inspect`, `ctrlflow`, `buildssa`) |
| `ImportObjectFact` / `ExportObjectFact` | **facts**: informații transmise de la un pachet la pachetele care îl importă |
| `Report` / `Reportf` | diagnosticul, opțional cu `SuggestedFixes` (pe care le aplică `--fix`) |

**Facts** fac posibile analizele între pachete. De exemplu, analizorul `printf` din `go vet` marchează funcțiile-wrapper ale lui `fmt.Printf`. Un pachet care le apelează, două niveluri mai sus, e verificat ca și cum ar apela `Printf` direct.

Același analizor rulează neschimbat în `go vet -vettool`, în `gopls` (diagnostic în editor), în `singlechecker`/`multichecker` (unealtă proprie) și în `golangci-lint`.

## Ce poate vedea un linter doar din sintaxă

Pentru un linter sintactic ajunge biblioteca standard (`go/parser`, `go/ast`). Exemplul de mai jos caută comparații `err == ErrX`, ca `errorlint`, dar fără informații de tip:

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strings"
)

const sursa = `package demo

func f(err error) bool {
	if err == ErrNotFound {
		return true
	}
	return err != nil && err == io.EOF
}
`

func main() {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "demo.go", sursa, 0)
	if err != nil {
		fmt.Println(err)
		return
	}
	ast.Inspect(file, func(n ast.Node) bool {
		bin, ok := n.(*ast.BinaryExpr)
		if !ok || (bin.Op != token.EQL && bin.Op != token.NEQ) {
			return true
		}
		if pareEroare(bin.X) && pareEroare(bin.Y) {
			fmt.Printf("%s: compară erori cu %s; folosește errors.Is\n", fset.Position(bin.Pos()), bin.Op)
		}
		return true
	})
}

// pareEroare ghicește după nume: fără informații de tip nu se poate mai bine.
func pareEroare(e ast.Expr) bool {
	switch v := e.(type) {
	case *ast.Ident:
		return v.Name == "err" || strings.HasPrefix(v.Name, "Err")
	case *ast.SelectorExpr:
		return strings.HasPrefix(v.Sel.Name, "Err") || v.Sel.Name == "EOF"
	}
	return false
}
```

Limita se vede imediat: verificarea depinde de **nume**. O variabilă de tip `error` numită `e` scapă, iar un `Errno` întreg ar fi semnalat greșit. Linterii reali (`errorlint`, `errcheck`, `copylocks`) folosesc `pass.TypesInfo` tocmai ca să știe tipul exact, de aceea au nevoie de pachete compilabile și cu tipuri verificate.

## Cache-ul

```bash
golangci-lint cache status   # Dir: ~/.cache/golangci-lint  Size: ...
golangci-lint cache clean
```

- Rezultatele analizei și **facts** se păstrează per pachet, cu o cheie formată din conținutul fișierelor, al dependențelor, versiunea linterului și configurația lui.
- Un pachet neschimbat nu se reanalizează; o modificare invalidează pachetul și pe cei care îl importă.
- Locația se schimbă cu `GOLANGCI_LINT_CACHE`; în CI, action-ul oficial salvează cache-ul între rulări.
- Și cache-ul de build al lui Go (`GOCACHE`) contează, pentru că `go/packages` folosește `go list`.

Pe proiecte mari, memoria devine limita. `GOGC=50` reduce memoria în schimbul timpului de rulare, iar `-j`/`--concurrency` limitează paralelismul.

## Lanțul de procesoare

Alertele brute nu ajung direct la ieșire. Ordinea aproximativă:

1. **typecheck**: erorile de compilare devin alerte.
2. **excluderi pe căi**: `exclusions.paths` și fișierele generate (`generated: lax | strict`).
3. **reguli de excludere**: `exclusions.rules` și `presets`.
4. **`//nolint`**: directivele din cod; `nolintlint` raportează la final directivele care n-au suprimat nimic.
5. **diff**: `--new`, `--new-from-rev`, `--new-from-merge-base` păstrează doar alertele de pe liniile modificate.
6. **limite**: `max-issues-per-linter`, `max-same-issues`, `uniq-by-line`.
7. **severitate**, **sortare**, **căi relative**.
8. **fixer**: aplică `SuggestedFixes` pentru `--fix`.

Severitatea contează în CI și în formate precum SARIF și code-climate:

```yaml
severity:
  default: error
  rules:
    - linters: [revive, gocritic]
      severity: warning
```

**Atenție la `max-same-issues: 3` implicit.** Dacă aceeași alertă apare de 50 de ori, vezi doar 3, deci raportul subestimează problema. La o primă evaluare a unui proiect, setează ambele limite la `0`.

## Linters proprii: Module Plugin System

Reguli specifice proiectului („niciun `time.Now()` direct în domeniu”, „toate handler-ele primesc `ctx`”) se adaugă printr-un plugin. Sistemul recomandat **recompilează** `golangci-lint` cu plugin-ul inclus.

**1. Plugin-ul** (un modul Go separat):

```go,ignore
package nopanic

import (
	"github.com/golangci/plugin-module-register/register"
	"golang.org/x/tools/go/analysis"
)

func init() {
	register.Plugin("nopanic", New)
}

type Settings struct {
	AllowInTests bool `json:"allow-in-tests"`
}

type plugin struct{ settings Settings }

func New(conf any) (register.LinterPlugin, error) {
	s, err := register.DecodeSettings[Settings](conf)
	if err != nil {
		return nil, err
	}
	return &plugin{settings: s}, nil
}

func (p *plugin) BuildAnalyzers() ([]*analysis.Analyzer, error) {
	return []*analysis.Analyzer{Analyzer}, nil
}

// LoadModeSyntax dacă ajunge AST-ul; LoadModeTypesInfo dacă folosești pass.TypesInfo.
func (p *plugin) GetLoadMode() string { return register.LoadModeTypesInfo }
```

**2. `.custom-gcl.yml`**, care descrie binarul personalizat:

```yaml
version: v2.15.0
name: custom-gcl
destination: ./bin
plugins:
  - module: github.com/firma/nopanic
    import: github.com/firma/nopanic
    version: v0.3.0
  # sau local, în timpul dezvoltării:
  # - module: github.com/firma/nopanic
  #   path: ./tools/nopanic
```

**3. Construirea și configurarea**:

```bash
golangci-lint custom        # produce ./bin/custom-gcl
./bin/custom-gcl run ./...
```

```yaml
version: "2"
linters:
  enable:
    - nopanic
  settings:
    custom:
      nopanic:
        type: module
        description: interzice panic în pachetele de bibliotecă
        settings:
          allow-in-tests: true
```

Alternativa veche, **Go Plugin System** (`.so` încărcat cu `plugin.Open`), cere ca plugin-ul și `golangci-lint` să fie compilate cu exact aceeași versiune de Go și aceleași versiuni ale dependențelor, și nu funcționează pe Windows. Module Plugin System elimină aceste probleme, pentru că totul se compilează într-un singur binar.

Pentru o regulă simplă, `forbidigo` (apeluri interzise prin regex) sau `depguard` (importuri interzise) ajung adesea, fără niciun plugin:

```yaml
linters:
  enable: [forbidigo, depguard]
  settings:
    forbidigo:
      forbid:
        - pattern: ^time\.Now$
          msg: folosește clock.Now() din internal/clock
    depguard:
      rules:
        domeniu:
          files: ["**/internal/domain/**"]
          deny:
            - pkg: net/http
              desc: domeniul nu depinde de transport
```

## Testarea unui analizor

`golang.org/x/tools/go/analysis/analysistest` rulează analizorul pe pachete din `testdata/src/...`, în care alertele așteptate sunt marcate prin comentarii:

```go,ignore
// testdata/src/lib/lib.go
package lib

func F() {
	panic("x") // want `panic în pachetul de bibliotecă lib`
}
```

```go,ignore
func TestAnalyzer(t *testing.T) {
	analysistest.Run(t, analysistest.TestData(), nopanic.Analyzer, "lib")
	// RunWithSuggestedFixes compară și rezultatul fix-urilor cu fișierele .golden
}
```

## Pe scurt

- Pachetele se încarcă o singură dată (`go/packages`); toți analizorii rulează în paralel pe aceleași AST-uri și tipuri.
- `analysis.Analyzer`: `Run(pass)`, `Requires`, `ResultOf`, facts între pachete, `SuggestedFixes` pentru `--fix`.
- Linterii sintactici ghicesc după nume; cei cu tipuri știu exact, dar cer cod compilabil.
- Cache per pachet, invalidat prin dependențe; `GOGC` și `-j` pentru memorie.
- Alertele trec prin procesoare: excluderi, `//nolint`, diff, limite (atenție la `max-same-issues: 3`), severitate.
- Linters proprii: Module Plugin System (`register.Plugin` + `.custom-gcl.yml` + `golangci-lint custom`); `analysistest` pentru teste.
