# Linting și golangci-lint — Practician

Configurația `.golangci.yml` în formatul v2, alegerea linterilor, suprimarea corectă a alertelor cu `//nolint` și integrarea în CI pe un proiect cu cod vechi.

## Fișierul de configurație

`golangci-lint` caută `.golangci.yml` (sau `.yaml`, `.toml`, `.json`) în directorul curent și urcă spre rădăcina proiectului. O configurație de proiect tipică:

```yaml
version: "2"

run:
  timeout: 5m
  tests: true            # analizează și fișierele _test.go (implicit)

linters:
  default: standard      # errcheck, govet, ineffassign, staticcheck, unused
  enable:
    - bodyclose
    - errorlint
    - gosec
    - revive
    - gocritic
    - misspell
    - nolintlint
  settings:
    errcheck:
      check-type-assertions: true   # și v := x.(T) fără ", ok"
    govet:
      enable:
        - shadow                    # analizor opțional, dezactivat implicit
    nolintlint:
      require-explanation: true
      require-specific: true
  exclusions:
    generated: lax                  # sare peste fișierele „Code generated ... DO NOT EDIT.”
    presets:
      - comments
      - std-error-handling
    rules:
      - path: _test\.go
        linters:
          - gosec
          - errcheck

formatters:
  enable:
    - gofmt
    - goimports

issues:
  max-issues-per-linter: 0   # 0 = fără limită (implicit 50)
  max-same-issues: 0         # 0 = fără limită (implicit 3)
```

```bash
golangci-lint config verify   # validează fișierul după schema JSON
golangci-lint config path     # ce fișier e folosit de fapt
```

## Cheia `version: "2"`

Fără ea, fișierul e tratat ca o configurație v1 și v2 refuză să ruleze. Diferențele importante față de v1:

| v1 | v2 |
|---|---|
| `enable-all: true` / `disable-all: true` | `linters.default: all` / `none` |
| `linters-settings:` | `linters.settings:` |
| `issues.exclude-rules` | `linters.exclusions.rules` |
| `issues.exclude-dirs`, `run.skip-dirs` | `linters.exclusions.paths` |
| `gofmt`, `goimports` în lista de linters | secțiunea separată `formatters` |
| `gosimple`, `stylecheck` linters separați | incluși în `staticcheck` |
| excluderi implicite ascunse | `linters.exclusions.presets`, alese explicit |

Conversia se face automat:

```bash
golangci-lint migrate        # rescrie configurația v1 în v2 (păstrează o copie)
```

## Alegerea setului de bază

`linters.default` stabilește punctul de plecare; `enable` și `disable` ajustează lista:

| Valoare | Înseamnă |
|---|---|
| `standard` | cei cinci linters de bază (implicit) |
| `all` | toți linterii; se folosește cu o listă `disable` |
| `none` | niciunul; activezi explicit tot ce vrei |
| `fast` | doar linterii rapizi (care nu au nevoie de informații de tip) |

`all` pare tentant, dar fiecare versiune nouă de `golangci-lint` aduce linters noi, deci un upgrade îți poate strica CI-ul. În practică, majoritatea proiectelor pornesc de la `standard` și adaugă o listă explicită.

Din linia de comandă:

```bash
golangci-lint run -E gosec -E errorlint       # activează în plus
golangci-lint run -D unused                   # dezactivează
golangci-lint run --enable-only errcheck      # doar acesta, ignorând configurația
golangci-lint run --default none -E govet
```

## Linters utili de adăugat

| Linter | Ce prinde |
|---|---|
| `errorlint` | `err == ErrX` și `err.(*T)` în loc de `errors.Is` / `errors.As`; `%v` în loc de `%w` |
| `bodyclose` | `resp.Body` de la `net/http` neînchis |
| `noctx` | cereri HTTP sau SQL fără `context.Context` |
| `sqlclosecheck`, `rowserrcheck` | `rows.Close()` și `rows.Err()` uitate |
| `gosec` | probleme de securitate (coduri `Gxxx`: SQL injection, criptografie slabă, permisiuni) |
| `revive` | stil, succesorul lui `golint` (comentarii de pachet, nume, mesaje de eroare) |
| `gocritic` | zeci de verificări de stil, performanță și diagnostic |
| `misspell` | greșeli de scriere în engleză în comentarii și stringuri |
| `nolintlint` | directive `//nolint` incorecte, nefolosite sau nejustificate |
| `exhaustive` | `switch` pe un enum care nu tratează toate valorile |
| `contextcheck` | funcții care nu propagă contextul primit |
| `nilerr`, `nilnil` | `return nil` după `err != nil`; `return nil, nil` |
| `unparam` | parametri sau rezultate mereu identice sau nefolosite |
| `unconvert` | conversii de tip inutile |
| `intrange`, `copyloopvar`, `modernize` | tipare vechi care au astăzi o formă mai simplă |
| `perfsprint` | `fmt.Sprintf` acolo unde `strconv` sau concatenarea sunt mai rapide |
| `prealloc` | slice-uri care ar putea fi prealocate |
| `gocyclo`, `gocognit`, `funlen`, `nestif` | complexitate: funcții prea lungi sau prea imbricate |
| `dupl`, `goconst` | cod duplicat; stringuri repetate care ar trebui să fie constante |
| `depguard`, `forbidigo` | importuri și apeluri interzise (de exemplu `fmt.Print` în producție) |
| `wrapcheck`, `err113` | erori externe neîmpachetate; erori dinamice în loc de sentinele |
| `testifylint`, `thelper`, `paralleltest`, `usetesting` | bune practici în teste |

## Suprimarea unei alerte: `//nolint`

Uneori linterul are dreptate doar în general. Directiva `//nolint` oprește raportarea, pe linia sau blocul pe care stă:

```go,ignore
_ = os.Remove(tmp)                       // varianta preferată: ignorare explicită

resp.Body.Close() //nolint:errcheck // închidere best-effort, răspunsul e deja citit

//nolint:gocyclo // parserul e o mașină de stări; spartă în funcții devine mai greu de citit
func parse(tokens []Token) (*AST, error) {
	// ...
}
```

Reguli:

- **Fără spațiu**: `//nolint:errcheck`, nu `// nolint:errcheck` (cu spațiu e un comentariu obișnuit și e ignorat).
- **Numește linterul**. Un `//nolint` gol ascunde **orice** problemă viitoare de pe linia aceea.
- **Adaugă motivul** după `//`.
- O directivă pe linia de deasupra unei funcții sau a unui `type` acoperă tot blocul.
- `//nolint:errcheck` dezactivează **doar** `errcheck`. Dacă activezi și `gosec`, aceeași eroare ignorată apare din nou, ca `G104: Errors unhandled`. Ori listezi ambii linters (`//nolint:errcheck,gosec`), ori tratezi eroarea.

`nolintlint` impune aceste reguli:

```text
main.go:65:8: directive `//nolint` should mention specific linter such as `//nolint:my-linter` (nolintlint)
main.go:67:24: directive `//nolint:errcheck` should provide explanation such as `//nolint:errcheck // this is why` (nolintlint)
```

Pentru reguli care țin de **fișiere sau directoare** întregi (teste, cod generat, `vendor/`) folosește `linters.exclusions` în configurație, nu `//nolint` presărat prin cod.

## Excluderi

```yaml
linters:
  exclusions:
    generated: lax      # lax | strict | disable
    paths:
      - third_party/
      - internal/legacy/
    rules:
      - path: _test\.go            # regex pe calea fișierului
        linters: [dupl, funlen]
      - text: "G104"               # regex pe mesaj
        linters: [gosec]
      - source: "^//go:generate "  # regex pe linia de cod
        linters: [lll]
    presets:
      - comments            # alertele de stil despre comentariile lipsă
      - std-error-handling  # erorile ignorate „acceptate” (Close, os.Remove, fmt.Fprint...)
      - common-false-positives
      - legacy
```

## Cod vechi: doar problemele noi

Pe un proiect mare, primul `golangci-lint run` poate raporta mii de probleme. Soluția practică e să blochezi **doar problemele noi**, apoi să le reduci pe cele vechi treptat:

```bash
golangci-lint run --new-from-rev=origin/main         # doar ce s-a schimbat față de main
golangci-lint run --new-from-merge-base=origin/main  # față de punctul de ramificare
golangci-lint run --new                              # doar modificările necomise
golangci-lint run --new-from-rev=HEAD~ --whole-files # tot fișierul atins, nu doar liniile noi
```

## În CI

GitHub Actions, cu action-ul oficial (are cache inclus și adnotează direct liniile din PR):

```yaml
name: lint
on: [push, pull_request]
permissions:
  contents: read
jobs:
  golangci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - uses: golangci/golangci-lint-action@v8
        with:
          version: v2.15     # fixează versiunea: altfel CI-ul se strică singur la un release nou
          # only-new-issues: true
```

**Fixează versiunea** atât în CI cât și local (de exemplu într-un `Makefile`). Versiuni diferite înseamnă linters și reguli diferite, deci rezultate diferite.

Formate de ieșire pentru alte sisteme:

```bash
golangci-lint run --output.json.path=report.json
golangci-lint run --output.sarif.path=report.sarif        # GitHub code scanning
golangci-lint run --output.junit-xml.path=report.xml      # GitLab, Jenkins
golangci-lint run --output.checkstyle.path=report.xml
golangci-lint run --issues-exit-code=0                    # raportează fără să pice build-ul
```

## Integrarea în editor

`gopls` rulează deja analizorii din `go vet` și o parte din `staticcheck`. Pentru `golangci-lint` complet în editor: VS Code are setarea `"go.lintTool": "golangci-lint-v2"`, iar GoLand are un plugin dedicat. Ideal, editorul, pre-commit-ul și CI-ul folosesc **aceeași** configurație și aceeași versiune.

## Pe scurt

- `.golangci.yml` cu `version: "2"`; `golangci-lint config verify` îl validează, `migrate` convertește din v1.
- `linters.default: standard` + o listă `enable` explicită; evită `all` fără o listă `disable`.
- `linters.settings` configurează fiecare linter; `formatters` e o secțiune separată.
- `//nolint:linter // motiv`, fără spațiu după `//`; `nolintlint` impune regula.
- `linters.exclusions` pentru căi, teste și cod generat.
- `--new-from-rev` pe cod vechi; versiunea fixată în CI și local.
