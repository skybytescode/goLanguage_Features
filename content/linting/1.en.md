# Linting and golangci-lint — Fundamentals

A **linter** reads code without running it and flags likely mistakes: ignored errors, values assigned for nothing, wrong `Printf` verbs. `golangci-lint` is the de facto standard tool in Go: it runs dozens of linters in a single command, with a single configuration.

## Why, if I already have the compiler?

The Go compiler is strict (unused variables and imports are errors), but it accepts plenty of wrong code. The program below compiles and runs, yet it has problems a linter catches immediately:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	name := "Ana"
	name = "Ion" // the value "Ana" is never used

	f, err := os.CreateTemp("", "demo")
	if err != nil {
		fmt.Println(err)
		return
	}
	defer os.Remove(f.Name())

	f.WriteString("hello") // the returned error is ignored
	f.Close()

	fmt.Printf("%d\n", name) // %d with a string
}
```

## The tool family

| Tool | What it does |
|---|---|
| `gofmt` | formats code; non-negotiable in Go |
| `go vet` | ships with the toolchain; near-certain mistakes (printf, copying a mutex, a forgotten `cancel`) |
| `staticcheck` | hundreds of checks: bugs, deprecated APIs, simplifications, style |
| `golangci-lint` | **aggregator**: runs `govet`, `staticcheck` and 100+ other linters in parallel, with caching and one shared configuration |

`golangci-lint` doesn't replace `go vet` and `staticcheck`, it **includes** them: `govet` and `staticcheck` are two of its linters.

## Installation

The official documentation recommends the **prebuilt binary**, with a pinned version:

```bash
# Linux/macOS: the binary goes into $(go env GOPATH)/bin
curl -sSfL https://golangci-lint.run/install.sh | sh -s -- -b $(go env GOPATH)/bin v2.15.0
# macOS
brew install golangci-lint
golangci-lint version
```

`go install` works but isn't recommended: the result depends on your local Go version and on the dependencies resolved on your machine.

## First run

```bash
golangci-lint run           # current package and subpackages (./... by default)
golangci-lint run ./...     # explicit: the whole module
golangci-lint run ./api/... # just one subtree
```

On the program above, the output looks like this:

```text
main.go:17:17: Error return value of `os.Remove` is not checked (errcheck)
main.go:19:15: Error return value of `f.WriteString` is not checked (errcheck)
main.go:20:9: Error return value of `f.Close` is not checked (errcheck)
main.go:22:14: printf: fmt.Printf format %d has arg name of wrong type string (govet)
main.go:9:2: ineffectual assignment to name (ineffassign)
5 issues:
* errcheck: 3
* govet: 1
* ineffassign: 1
```

Note that `defer os.Remove(...)` shows up too: `errcheck` makes no exception for `defer`. When you really mean to ignore an error, say so explicitly with `_ =`, so it reads as a decision, not an oversight.

Every line has the form **`file:line:column: message (linter)`**. The linter name in parentheses matters: you use it to look up documentation, to configure the linter, or to suppress a report.

The **exit code** is `1` when there are issues and `0` when there are none. That's how CI fails a build.

## Linters enabled by default

Without a configuration, `golangci-lint` v2 runs the **`standard`** set of five linters:

| Linter | What it catches |
|---|---|
| `errcheck` | returned errors that are ignored (`f.Close()`, `json.Unmarshal(...)` without `err`) |
| `govet` | the `go vet` analyzers: printf, copylocks, lostcancel, structtag, unreachable... |
| `ineffassign` | assignments whose value is never read |
| `staticcheck` | bugs (SA), simplifications (S), style (ST), quick fixes (QF) |
| `unused` | unused constants, variables, functions and types |

```bash
golangci-lint linters       # what's enabled and what's available, with descriptions
golangci-lint help linters  # every known linter
```

## Formatting: `golangci-lint fmt`

Since v2, formatters (`gofmt`, `goimports`, `gofumpt`, `gci`, `golines`) have their own command:

```bash
golangci-lint fmt           # format files in place
golangci-lint fmt --diff    # only show the differences
```

## Automatic fixes: `--fix`

Some linters can fix their own findings (`golangci-lint linters` marks them `[auto-fix]`):

```bash
golangci-lint run --fix
```

Whatever can't be fixed automatically (an ignored error, for example, where only you know the right handling) stays in the report.

## The fixed program

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	name := "Ion"

	f, err := os.CreateTemp("", "demo")
	if err != nil {
		fmt.Println(err)
		return
	}
	defer func() { _ = os.Remove(f.Name()) }() // temp file: the error doesn't matter

	if _, err := f.WriteString("hello"); err != nil {
		fmt.Println("write:", err)
		return
	}
	if err := f.Close(); err != nil {
		fmt.Println("close:", err)
		return
	}

	fmt.Printf("%s\n", name)
}
```

## In short

- A linter finds code that compiles but is wrong or suspicious.
- `golangci-lint` runs many linters at once; `govet` and `staticcheck` are included.
- The default (`standard`) set: `errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`.
- `golangci-lint run ./...`; output is `file:line:column: message (linter)`, exit code 1 when there are issues.
- `golangci-lint fmt` formats, `run --fix` applies automatic fixes.
- Install the pinned binary, not via `go install`.
