# Linting and golangci-lint — Expert

How `golangci-lint` works under the hood: package loading, the `go/analysis` framework, the cache, the issue-processing pipeline, and writing your own linter, integrated as a plugin.

## Anatomy of a run

```text
configuration ─► package loading (go/packages) ─► analyzers (go/analysis) ─► processors ─► output
                  AST + types, done once            all linters, in parallel   filter, sort   text/json/sarif
```

1. **Configuration**: `.golangci.yml`, flags and defaults decide the final list of linters and formatters.
2. **Loading**: `golang.org/x/tools/go/packages` reads the packages (with `go list` underneath), parses them and type-checks them. This is the most expensive stage, so it happens **once** for all linters.
3. **Analysis**: almost every linter is an `analysis.Analyzer`. `golangci-lint` groups them into a single "metalinter" (`goanalysis_metalinter`) that runs them in parallel, over the same ASTs and type information.
4. **Processing**: raw issues go through a chain of processors that filter, deduplicate and sort.
5. **Output**: one or more formats, simultaneously.

That's why `golangci-lint` is much faster than running 20 separate tools, each loading packages on its own.

## The `go/analysis` framework

An analyzer is a value, not a program:

```go,ignore
var Analyzer = &analysis.Analyzer{
	Name:     "nopanic",
	Doc:      "reports panic calls in non-main packages",
	Requires: []*analysis.Analyzer{inspect.Analyzer}, // reuse another analyzer's result
	Run:      run,
}

func run(pass *analysis.Pass) (any, error) {
	if pass.Pkg.Name() == "main" {
		return nil, nil
	}
	ins := pass.ResultOf[inspect.Analyzer].(*inspector.Inspector)
	ins.Preorder([]ast.Node{(*ast.CallExpr)(nil)}, func(n ast.Node) {
		call := n.(*ast.CallExpr)
		id, ok := call.Fun.(*ast.Ident)
		if !ok {
			return
		}
		// TypesInfo tells the panic built-in apart from a user function named panic
		if b, ok := pass.TypesInfo.Uses[id].(*types.Builtin); ok && b.Name() == "panic" {
			pass.Reportf(call.Pos(), "panic in library package %s", pass.Pkg.Name())
		}
	})
	return nil, nil
}
```

The important parts of `analysis.Pass`:

| Field | What it gives you |
|---|---|
| `Files []*ast.File` | the package's syntax trees |
| `TypesInfo *types.Info` | the type of every expression, the object every identifier refers to |
| `Pkg *types.Package` | the current package, with its scope |
| `ResultOf` | results of the analyzers in `Requires` (for example `inspect`, `ctrlflow`, `buildssa`) |
| `ImportObjectFact` / `ExportObjectFact` | **facts**: information passed from a package to the packages that import it |
| `Report` / `Reportf` | the diagnostic, optionally with `SuggestedFixes` (which `--fix` applies) |

**Facts** make cross-package analysis possible. For example, `go vet`'s `printf` analyzer marks the wrappers of `fmt.Printf`. A package calling them two levels up is checked as if it called `Printf` directly.

The same analyzer runs unchanged in `go vet -vettool`, in `gopls` (editor diagnostics), in `singlechecker`/`multichecker` (your own tool) and in `golangci-lint`.

## What a linter can see from syntax alone

A syntactic linter only needs the standard library (`go/parser`, `go/ast`). The example below looks for `err == ErrX` comparisons, like `errorlint`, but without type information:

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strings"
)

const source = `package demo

func f(err error) bool {
	if err == ErrNotFound {
		return true
	}
	return err != nil && err == io.EOF
}
`

func main() {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "demo.go", source, 0)
	if err != nil {
		fmt.Println(err)
		return
	}
	ast.Inspect(file, func(n ast.Node) bool {
		bin, ok := n.(*ast.BinaryExpr)
		if !ok || (bin.Op != token.EQL && bin.Op != token.NEQ) {
			return true
		}
		if looksLikeError(bin.X) && looksLikeError(bin.Y) {
			fmt.Printf("%s: compares errors with %s; use errors.Is\n", fset.Position(bin.Pos()), bin.Op)
		}
		return true
	})
}

// looksLikeError guesses from the name: without type information there's no better way.
func looksLikeError(e ast.Expr) bool {
	switch v := e.(type) {
	case *ast.Ident:
		return v.Name == "err" || strings.HasPrefix(v.Name, "Err")
	case *ast.SelectorExpr:
		return strings.HasPrefix(v.Sel.Name, "Err") || v.Sel.Name == "EOF"
	}
	return false
}
```

The limitation is obvious: the check depends on **names**. An `error` variable called `e` slips through, and an integer `Errno` would be flagged by mistake. Real linters (`errorlint`, `errcheck`, `copylocks`) use `pass.TypesInfo` precisely to know the exact type, which is why they need packages that compile and type-check.

## The cache

```bash
golangci-lint cache status   # Dir: ~/.cache/golangci-lint  Size: ...
golangci-lint cache clean
```

- Analysis results and **facts** are stored per package, keyed by the contents of the files and dependencies, the linter version and its configuration.
- An unchanged package isn't reanalyzed; a change invalidates the package and its importers.
- Change the location with `GOLANGCI_LINT_CACHE`; in CI the official action saves the cache between runs.
- Go's build cache (`GOCACHE`) matters too, since `go/packages` uses `go list`.

On large projects memory becomes the limit. `GOGC=50` lowers memory at the cost of run time, and `-j`/`--concurrency` limits parallelism.

## The processor pipeline

Raw issues don't go straight to the output. The approximate order:

1. **typecheck**: compile errors become issues.
2. **path exclusions**: `exclusions.paths` and generated files (`generated: lax | strict`).
3. **exclusion rules**: `exclusions.rules` and `presets`.
4. **`//nolint`**: the directives in the code; `nolintlint` reports at the end the directives that suppressed nothing.
5. **diff**: `--new`, `--new-from-rev`, `--new-from-merge-base` keep only issues on changed lines.
6. **limits**: `max-issues-per-linter`, `max-same-issues`, `uniq-by-line`.
7. **severity**, **sorting**, **relative paths**.
8. **fixer**: applies `SuggestedFixes` for `--fix`.

Severity matters in CI and in formats such as SARIF and code-climate:

```yaml
severity:
  default: error
  rules:
    - linters: [revive, gocritic]
      severity: warning
```

**Watch out for the default `max-same-issues: 3`.** If the same issue occurs 50 times, you only see 3, so the report understates the problem. For a first assessment of a project, set both limits to `0`.

## Custom linters: the Module Plugin System

Project-specific rules ("no direct `time.Now()` in the domain", "every handler takes a `ctx`") are added via a plugin. The recommended system **rebuilds** `golangci-lint` with the plugin compiled in.

**1. The plugin** (a separate Go module):

```go,ignore
package nopanic

import (
	"github.com/golangci/plugin-module-register/register"
	"golang.org/x/tools/go/analysis"
)

func init() {
	register.Plugin("nopanic", New)
}

type Settings struct {
	AllowInTests bool `json:"allow-in-tests"`
}

type plugin struct{ settings Settings }

func New(conf any) (register.LinterPlugin, error) {
	s, err := register.DecodeSettings[Settings](conf)
	if err != nil {
		return nil, err
	}
	return &plugin{settings: s}, nil
}

func (p *plugin) BuildAnalyzers() ([]*analysis.Analyzer, error) {
	return []*analysis.Analyzer{Analyzer}, nil
}

// LoadModeSyntax if the AST is enough; LoadModeTypesInfo if you use pass.TypesInfo.
func (p *plugin) GetLoadMode() string { return register.LoadModeTypesInfo }
```

**2. `.custom-gcl.yml`**, describing the custom binary:

```yaml
version: v2.15.0
name: custom-gcl
destination: ./bin
plugins:
  - module: github.com/company/nopanic
    import: github.com/company/nopanic
    version: v0.3.0
  # or locally, during development:
  # - module: github.com/company/nopanic
  #   path: ./tools/nopanic
```

**3. Building and configuring**:

```bash
golangci-lint custom        # produces ./bin/custom-gcl
./bin/custom-gcl run ./...
```

```yaml
version: "2"
linters:
  enable:
    - nopanic
  settings:
    custom:
      nopanic:
        type: module
        description: forbids panic in library packages
        settings:
          allow-in-tests: true
```

The older alternative, the **Go Plugin System** (a `.so` loaded with `plugin.Open`), requires the plugin and `golangci-lint` to be built with exactly the same Go version and dependency versions, and doesn't work on Windows. The Module Plugin System removes those problems, because everything is compiled into a single binary.

For a simple rule, `forbidigo` (forbidden calls via regex) or `depguard` (forbidden imports) is often enough, no plugin needed:

```yaml
linters:
  enable: [forbidigo, depguard]
  settings:
    forbidigo:
      forbid:
        - pattern: ^time\.Now$
          msg: use clock.Now() from internal/clock
    depguard:
      rules:
        domain:
          files: ["**/internal/domain/**"]
          deny:
            - pkg: net/http
              desc: the domain doesn't depend on the transport
```

## Testing an analyzer

`golang.org/x/tools/go/analysis/analysistest` runs the analyzer on packages under `testdata/src/...`, where the expected issues are marked with comments:

```go,ignore
// testdata/src/lib/lib.go
package lib

func F() {
	panic("x") // want `panic in library package lib`
}
```

```go,ignore
func TestAnalyzer(t *testing.T) {
	analysistest.Run(t, analysistest.TestData(), nopanic.Analyzer, "lib")
	// RunWithSuggestedFixes also compares the result of the fixes with .golden files
}
```

## In short

- Packages are loaded once (`go/packages`); every analyzer runs in parallel over the same ASTs and types.
- `analysis.Analyzer`: `Run(pass)`, `Requires`, `ResultOf`, cross-package facts, `SuggestedFixes` for `--fix`.
- Syntactic linters guess from names; type-aware ones know exactly, but need compiling code.
- Per-package cache, invalidated through dependencies; `GOGC` and `-j` for memory.
- Issues go through processors: exclusions, `//nolint`, diff, limits (watch out for `max-same-issues: 3`), severity.
- Custom linters: the Module Plugin System (`register.Plugin` + `.custom-gcl.yml` + `golangci-lint custom`); `analysistest` for tests.
