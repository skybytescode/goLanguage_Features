# Linting and golangci-lint — Practitioner

The `.golangci.yml` configuration in the v2 format, choosing linters, suppressing reports properly with `//nolint`, and wiring it into CI on a project with legacy code.

## The configuration file

`golangci-lint` looks for `.golangci.yml` (or `.yaml`, `.toml`, `.json`) in the current directory and walks up towards the project root. A typical project configuration:

```yaml
version: "2"

run:
  timeout: 5m
  tests: true            # analyze _test.go files too (the default)

linters:
  default: standard      # errcheck, govet, ineffassign, staticcheck, unused
  enable:
    - bodyclose
    - errorlint
    - gosec
    - revive
    - gocritic
    - misspell
    - nolintlint
  settings:
    errcheck:
      check-type-assertions: true   # also v := x.(T) without ", ok"
    govet:
      enable:
        - shadow                    # optional analyzer, off by default
    nolintlint:
      require-explanation: true
      require-specific: true
  exclusions:
    generated: lax                  # skip "Code generated ... DO NOT EDIT." files
    presets:
      - comments
      - std-error-handling
    rules:
      - path: _test\.go
        linters:
          - gosec
          - errcheck

formatters:
  enable:
    - gofmt
    - goimports

issues:
  max-issues-per-linter: 0   # 0 = unlimited (default 50)
  max-same-issues: 0         # 0 = unlimited (default 3)
```

```bash
golangci-lint config verify   # validate the file against the JSON schema
golangci-lint config path     # which file is actually used
```

## The `version: "2"` key

Without it, the file is treated as a v1 configuration and v2 refuses to run. The important differences from v1:

| v1 | v2 |
|---|---|
| `enable-all: true` / `disable-all: true` | `linters.default: all` / `none` |
| `linters-settings:` | `linters.settings:` |
| `issues.exclude-rules` | `linters.exclusions.rules` |
| `issues.exclude-dirs`, `run.skip-dirs` | `linters.exclusions.paths` |
| `gofmt`, `goimports` in the linters list | a separate `formatters` section |
| `gosimple`, `stylecheck` as separate linters | merged into `staticcheck` |
| hidden default exclusions | `linters.exclusions.presets`, chosen explicitly |

Conversion is automatic:

```bash
golangci-lint migrate        # rewrite a v1 configuration as v2 (keeps a backup)
```

## Choosing the base set

`linters.default` sets the starting point; `enable` and `disable` adjust the list:

| Value | Meaning |
|---|---|
| `standard` | the five base linters (the default) |
| `all` | every linter; used together with a `disable` list |
| `none` | nothing; you enable everything explicitly |
| `fast` | only fast linters (those that don't need type information) |

`all` looks tempting, but every new `golangci-lint` release brings new linters, so an upgrade can break your CI. In practice most projects start from `standard` and add an explicit list.

From the command line:

```bash
golangci-lint run -E gosec -E errorlint       # enable additionally
golangci-lint run -D unused                   # disable
golangci-lint run --enable-only errcheck      # only this one, ignoring the configuration
golangci-lint run --default none -E govet
```

## Useful linters to add

| Linter | What it catches |
|---|---|
| `errorlint` | `err == ErrX` and `err.(*T)` instead of `errors.Is` / `errors.As`; `%v` instead of `%w` |
| `bodyclose` | an unclosed `resp.Body` from `net/http` |
| `noctx` | HTTP or SQL requests without a `context.Context` |
| `sqlclosecheck`, `rowserrcheck` | forgotten `rows.Close()` and `rows.Err()` |
| `gosec` | security issues (`Gxxx` codes: SQL injection, weak crypto, permissions) |
| `revive` | style, the successor of `golint` (package comments, names, error messages) |
| `gocritic` | dozens of style, performance and diagnostic checks |
| `misspell` | English spelling mistakes in comments and strings |
| `nolintlint` | malformed, unused or unexplained `//nolint` directives |
| `exhaustive` | a `switch` on an enum that doesn't handle every value |
| `contextcheck` | functions that don't propagate the context they received |
| `nilerr`, `nilnil` | `return nil` after `err != nil`; `return nil, nil` |
| `unparam` | parameters or results that are always the same or unused |
| `unconvert` | unnecessary type conversions |
| `intrange`, `copyloopvar`, `modernize` | old patterns that have a simpler form today |
| `perfsprint` | `fmt.Sprintf` where `strconv` or concatenation is faster |
| `prealloc` | slices that could be preallocated |
| `gocyclo`, `gocognit`, `funlen`, `nestif` | complexity: functions that are too long or too nested |
| `dupl`, `goconst` | duplicated code; repeated strings that should be constants |
| `depguard`, `forbidigo` | forbidden imports and calls (`fmt.Print` in production code, say) |
| `wrapcheck`, `err113` | unwrapped external errors; dynamic errors instead of sentinels |
| `testifylint`, `thelper`, `paralleltest`, `usetesting` | testing best practices |

## Suppressing a report: `//nolint`

Sometimes the linter is only right in general. The `//nolint` directive stops reporting on the line or block it sits on:

```go,ignore
_ = os.Remove(tmp)                       // preferred: an explicit ignore

resp.Body.Close() //nolint:errcheck // best-effort close, the response is already read

//nolint:gocyclo // the parser is a state machine; split into functions it becomes harder to read
func parse(tokens []Token) (*AST, error) {
	// ...
}
```

Rules:

- **No space**: `//nolint:errcheck`, not `// nolint:errcheck` (with a space it's an ordinary comment and it's ignored).
- **Name the linter**. A bare `//nolint` hides **any** future issue on that line.
- **Add the reason** after `//`.
- A directive on the line above a function or `type` covers the whole block.
- `//nolint:errcheck` disables **only** `errcheck`. If `gosec` is enabled too, the same ignored error comes back as `G104: Errors unhandled`. Either list both linters (`//nolint:errcheck,gosec`) or handle the error.

`nolintlint` enforces these rules:

```text
main.go:65:8: directive `//nolint` should mention specific linter such as `//nolint:my-linter` (nolintlint)
main.go:67:24: directive `//nolint:errcheck` should provide explanation such as `//nolint:errcheck // this is why` (nolintlint)
```

For rules about whole **files or directories** (tests, generated code, `vendor/`), use `linters.exclusions` in the configuration, not `//nolint` scattered through the code.

## Exclusions

```yaml
linters:
  exclusions:
    generated: lax      # lax | strict | disable
    paths:
      - third_party/
      - internal/legacy/
    rules:
      - path: _test\.go            # regex on the file path
        linters: [dupl, funlen]
      - text: "G104"               # regex on the message
        linters: [gosec]
      - source: "^//go:generate "  # regex on the source line
        linters: [lll]
    presets:
      - comments            # style reports about missing comments
      - std-error-handling  # "accepted" ignored errors (Close, os.Remove, fmt.Fprint...)
      - common-false-positives
      - legacy
```

## Legacy code: only new issues

On a large project, the first `golangci-lint run` can report thousands of issues. The practical approach is to block **only new issues**, then reduce the old ones gradually:

```bash
golangci-lint run --new-from-rev=origin/main         # only what changed relative to main
golangci-lint run --new-from-merge-base=origin/main  # relative to the branch point
golangci-lint run --new                              # only uncommitted changes
golangci-lint run --new-from-rev=HEAD~ --whole-files # the whole touched file, not just new lines
```

## In CI

GitHub Actions, with the official action (it has caching built in and annotates PR lines directly):

```yaml
name: lint
on: [push, pull_request]
permissions:
  contents: read
jobs:
  golangci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - uses: golangci/golangci-lint-action@v8
        with:
          version: v2.15     # pin it: otherwise CI breaks on its own when a new release ships
          # only-new-issues: true
```

**Pin the version** both in CI and locally (in a `Makefile`, say). Different versions mean different linters and rules, so different results.

Output formats for other systems:

```bash
golangci-lint run --output.json.path=report.json
golangci-lint run --output.sarif.path=report.sarif        # GitHub code scanning
golangci-lint run --output.junit-xml.path=report.xml      # GitLab, Jenkins
golangci-lint run --output.checkstyle.path=report.xml
golangci-lint run --issues-exit-code=0                    # report without failing the build
```

## Editor integration

`gopls` already runs the `go vet` analyzers and part of `staticcheck`. For full `golangci-lint` in the editor, VS Code has the setting `"go.lintTool": "golangci-lint-v2"`, and GoLand has a dedicated plugin. Ideally the editor, the pre-commit hook and CI all use the **same** configuration and the same version.

## In short

- `.golangci.yml` with `version: "2"`; `golangci-lint config verify` validates it, `migrate` converts from v1.
- `linters.default: standard` plus an explicit `enable` list; avoid `all` without a `disable` list.
- `linters.settings` configures each linter; `formatters` is a separate section.
- `//nolint:linter // reason`, no space after `//`; `nolintlint` enforces it.
- `linters.exclusions` for paths, tests and generated code.
- `--new-from-rev` on legacy code; a pinned version in CI and locally.
