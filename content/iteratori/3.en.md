# Range and iterators — Advanced

Why Go's iterators are "push", the rules an iterator must follow (and what happens when it doesn't), single-use iterators, and how to report errors from an iterator.

## Why push, not pull

Most languages use **pull** iterators: an object with `Next()`, called by the `for` loop. Go chose **push** iterators: the iterator is a function that calls the loop body. The reasons:

- **The iterator's code is ordinary code.** Walking a tree is a normal recursive function calling `yield`; the pull version would have to become a state machine with an explicit stack.
- **Cleanup is natural.** A `defer` in the iterator runs at the end or on `break`; a pull iterator needs a `Close` method the caller can forget.
- **Performance.** A small push iterator can be fully inlined together with the loop body.

For the rare cases where you really need pull (walking two iterators in parallel), `iter.Pull` does the conversion (see [Range and iterators](../../iteratori/4/)).

## Run-time checks

Because the iterator is code anyone can write, the compiler adds checks around `yield`. Violations panic with explicit messages:

```go,panic
package main

import "fmt"

// Bad ignores yield's result.
func Bad(yield func(int) bool) {
	yield(1)
	yield(2) // called after the loop did a break
}

func main() {
	for x := range Bad {
		fmt.Println(x)
		break
	}
	// panic: runtime error: range function continued iteration after function for loop body returned false
}
```

Other detected situations: calling `yield` after the iterator returned, or an iterator that "swallows" a panic from the loop body and keeps going.

## Single-use iterators

`iter.Seq` doesn't say whether the iterator can be walked more than once. Those built over collections (`slices.Values`, `maps.Keys`) can be restarted; those built over a stream (lines read from an `io.Reader`, the results of an SQL query) usually can't. The standard library's convention is to document single-use iterators explicitly.

## Errors in iterators

An `iter.Seq[V]` has nowhere to return an error. Two common patterns:

```go,ignore
// 1. Seq2 with an error per element
func Rows(db *sql.DB) iter.Seq2[Row, error]

// 2. an iterator + an Err() method, like bufio.Scanner
it := NewReader(r)
for v := range it.All() { ... }
if err := it.Err(); err != nil { ... }
```

## Iterators in APIs

When you expose or accept a sequence, choosing between a slice and an iterator says something about the contract:

| Return… | When |
|---|---|
| `[]T` | the result is small, already computed, and the caller may walk it several times or modify it |
| `iter.Seq[T]` | the result is large, computed lazily, infinite, or built from an internal structure you don't want to expose |
| `iter.Seq2[T, error]` | each element may fail (reading files, the network, databases) |

| Accept… | When |
|---|---|
| `[]T` | you need `len`, random access or several passes |
| `iter.Seq[T]` | you walk it once; the caller can pass a slice (`slices.Values(s)`), a map, a generator |

The standard library's naming conventions: `All()` for index/key–value pairs, `Values()` and `Keys()` for a single component, `Backward()` for reverse order. Functions consuming iterators are named after the result (`Collect`, `Sorted`, `Insert`, `AppendSeq`).

## Summary

- Push: the iterator is ordinary code, cleanup is a `defer`, and inlining makes it fast.
- Calling `yield` after `false` or after returning panics with an explicit message.
- Document single-use iterators (streams, queries).
- Errors are reported through `Seq2[V, error]` or an `Err()` method.
- Return `iter.Seq` for large or lazy results; accept `iter.Seq` when you walk the sequence once.
