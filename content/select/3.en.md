# Select — Advanced

What `select` does and doesn't guarantee: the limits of fairness, `select` with a variable number of cases via `reflect.Select`, and the new timer semantics of Go 1.23.

## Fairness has a limit

The choice is uniform **only among cases ready at the same moment**. A case that's always ready (say a buffered channel that's always full) is chosen about `1/n` of the time; if one source produces much faster than another, it dominates. Fairness between producers is solved in the architecture (separate queues, limiting), not in `select`.

## A variable number of cases: `reflect.Select`

The number of cases in a `select` is fixed at compile time. For N channels known only at run time there's `reflect.Select`:

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	sources := make([]chan int, 3)
	cases := make([]reflect.SelectCase, len(sources))
	for i := range sources {
		sources[i] = make(chan int, 1)
		cases[i] = reflect.SelectCase{Dir: reflect.SelectRecv, Chan: reflect.ValueOf(sources[i])}
	}
	sources[1] <- 42

	chosen, value, ok := reflect.Select(cases)
	fmt.Println(chosen, value.Int(), ok) // 1 42 true
}
```

It's several times slower than a static `select` (reflection and allocations). For many sources, a fan-in into a single channel (see [Channels](../../channels/2/)) is usually better.

## Timers in Go 1.23

The timer implementation was rewritten in Go 1.23, with direct effects on `select`:

- a timer's channel (`timer.C`, `time.After`) is now **synchronous** (unbuffered, as far as the program can tell): no value "lingers" in the channel after `Stop` or `Reset`;
- timers are tied to their channel, and an unstopped timer with no remaining references is **collected by the GC**; `time.After` in a loop no longer leaks memory.

The new behavior applies to modules with `go 1.23` or newer in `go.mod`; `GODEBUG=asynctimerchan=1` reverts to the old one.

## The random choice, observed

When both cases are ready, each is chosen with roughly the same probability. Code that assumes "the first case written" wins is wrong, even if it passes a few tests:

```go
package main

import "fmt"

func main() {
	a, b := make(chan int, 1), make(chan int, 1)
	var chosen [2]int
	for range 10_000 {
		a <- 1
		b <- 1
		select {
		case <-a:
			chosen[0]++
			<-b
		case <-b:
			chosen[1]++
			<-a
		}
	}
	fmt.Println("a:", chosen[0], "b:", chosen[1]) // roughly 5000 / 5000
}
```

The randomization is intentional, for the same reason as map order: no program should come to depend on an order that isn't guaranteed. If a case must take priority, check it explicitly in a separate `select` (see the Practitioner level).

## Summary

- The choice is uniform only among cases ready at the same time; fairness between producers is an architecture concern.
- `reflect.Select` for dynamic N, at a much higher cost.
- Since Go 1.23, timers are synchronous (no stale values after `Reset`) and collectable.
- Among cases ready at the same time, the choice is uniform; priority must be implemented explicitly.
