# Select — Avansat

Ce garantează și ce nu garantează `select`: limitele echității, `select` cu număr variabil de cazuri prin `reflect.Select` și noua semantică a timerelor din Go 1.23.

## Echitatea are o limită

Alegerea e uniformă **doar între cazurile gata în același moment**. Un caz care e mereu gata (de exemplu un channel cu buffer mereu plin) va fi ales de aproximativ `1/n` ori; dacă o sursă produce mult mai repede decât alta, ea va domina. Echitatea între producători se rezolvă în arhitectură (cozi separate, limitare), nu în `select`.

## `select` cu număr variabil de cazuri: `reflect.Select`

Numărul de cazuri al unui `select` e fix la compilare. Pentru N channels cunoscute doar la rulare există `reflect.Select`:

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	surse := make([]chan int, 3)
	cazuri := make([]reflect.SelectCase, len(surse))
	for i := range surse {
		surse[i] = make(chan int, 1)
		cazuri[i] = reflect.SelectCase{Dir: reflect.SelectRecv, Chan: reflect.ValueOf(surse[i])}
	}
	surse[1] <- 42

	ales, valoare, ok := reflect.Select(cazuri)
	fmt.Println(ales, valoare.Int(), ok) // 1 42 true
}
```

E de câteva ori mai lent decât un `select` static (reflection și alocări). Pentru multe surse, un fan-in într-un singur channel (vezi [Channels](../../channels/2/)) e de obicei mai bun.

## Timerele în Go 1.23

Implementarea timerelor a fost rescrisă în Go 1.23, cu efecte directe asupra `select`:

- channel-ul unui timer (`timer.C`, `time.After`) e acum **sincron** (fără buffer, din perspectiva programului): o valoare nu „stă” în channel după `Stop` sau `Reset`;
- timerele sunt legate de channel, iar un timer neoprit, la care nu mai există referințe, e **colectat de GC**; `time.After` într-o buclă nu mai produce scurgeri de memorie.

Comportamentul nou e activ pentru modulele cu `go 1.23` sau mai nou în `go.mod`; `GODEBUG=asynctimerchan=1` îl revine la cel vechi.

## Alegerea aleatoare, observată

Când ambele cazuri sunt gata, fiecare e ales cu aproximativ aceeași probabilitate. Codul care presupune că „primul caz scris” câștigă e greșit, chiar dacă trece câteva teste:

```go
package main

import "fmt"

func main() {
	a, b := make(chan int, 1), make(chan int, 1)
	var alese [2]int
	for range 10_000 {
		a <- 1
		b <- 1
		select {
		case <-a:
			alese[0]++
			<-b
		case <-b:
			alese[1]++
			<-a
		}
	}
	fmt.Println("a:", alese[0], "b:", alese[1]) // aproximativ 5000 / 5000
}
```

Aleatorizarea e intenționată, din același motiv ca la ordinea în maps: niciun program să nu ajungă să depindă de o ordine care nu e garantată. Dacă un caz trebuie să aibă prioritate, verifică-l explicit într-un `select` separat (vezi nivelul Practician).

## Pe scurt

- Alegerea e uniformă doar între cazurile gata simultan; echitatea între producători ține de arhitectură.
- `reflect.Select` pentru N dinamic, cu un cost mult mai mare.
- Din Go 1.23, timerele sunt sincrone (fără valori vechi după `Reset`) și colectabile.
- Între cazurile gata simultan, alegerea e uniformă; prioritatea se implementează explicit.
