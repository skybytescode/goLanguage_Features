# Control flow — Advanced

The exact semantics of control statements: what `range` does with the expression it walks, why map order is random, how strings are decoded, what happens to `defer` in loops, and what the spec does (and doesn't) guarantee about evaluation order.

## `range` evaluates its expression once

The expression after `range` is evaluated **once**, before the first iteration. For slices, the length is fixed at that point; appends inside the loop don't extend it:

```go
package main

import "fmt"

func main() {
	s := []int{1, 2, 3}
	for i, v := range s {
		if i == 0 {
			s = append(s, 99) // s now points to a different, longer array
		}
		fmt.Print(v, " ")
	}
	fmt.Println("\nlen:", len(s)) // the loop ran 3 times, but len is 4
}
```

For an **array** (not a slice), `range` walks a **copy** of it. Changes made inside the loop don't show up in the values you receive:

```go
package main

import "fmt"

func main() {
	arr := [3]int{1, 2, 3}
	for i, v := range arr { // a copy of the array
		arr[2] = 100
		fmt.Print(i, ":", v, " ") // 0:1 1:2 2:3
	}
	fmt.Println()
	for i, v := range &arr { // pointer: no copy
		arr[2] = 200
		fmt.Print(i, ":", v, " ") // 0:1 1:2 2:200
	}
	fmt.Println()
}
```

The value `v` is always a copy of the element. To modify the elements of a slice of structs, use the index: `s[i].Field = x`. For large arrays of structs, `for i := range s` also avoids copying every element.

## Map order is random on purpose

The runtime picks a random starting point for every `range` over a map, so nobody can depend on an order. Deleting a key during iteration is safe; a key added during iteration **may or may not** show up.

```go
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	m := map[string]int{"c": 3, "a": 1, "b": 2}
	for _, k := range slices.Sorted(maps.Keys(m)) { // stable order
		fmt.Println(k, m[k])
	}
}
```

## `range` over a string decodes UTF-8

The steps are characters, not bytes. Invalid bytes produce `U+FFFD` and advance by a single byte:

```go
package main

import "fmt"

func main() {
	for i, r := range "aș\xffb" {
		fmt.Printf("%d:%q ", i, r) // 0:'a' 1:'ș' 3:'�' 4:'b'
	}
	fmt.Println()
}
```

## `defer` in loops

`defer` runs when the **function** returns, not at the end of the iteration. In a loop that opens files, they all stay open until the end:

```go,ignore
for _, name := range files {
	f, err := os.Open(name)
	if err != nil {
		return err
	}
	defer f.Close() // piles up: they all close only at return
	// ...
}
```

The fix is to move the loop body into a separate function, where `defer` runs on every call.

## Order of evaluation

The spec guarantees that **function calls, method calls, channel receive operations and logical operators** in an expression are evaluated left to right. For **the other** operands (variables, indexing, fields), their order relative to calls is **unspecified**:

```go
package main

import "fmt"

func main() {
	x := 1
	inc := func() int { x++; return x }

	// inc() is called before fmt.Println, but whether x (the second argument)
	// is read before or after the call is not specified by the language
	fmt.Println(inc(), x) // 2 1 or 2 2, depending on the compiler
}
```

The practical rule: don't write expressions where a call modifies a variable read in the **same** expression. Split them into separate statements.

Multiple assignments have two well-defined phases: first **all** the operands on the left (indices, dereferences) and every expression on the right are evaluated, then the assignments happen left to right. That's why swapping is safe:

```go
package main

import "fmt"

func main() {
	a, b := 1, 2
	a, b = b, a // the right side is fully evaluated before any assignment
	fmt.Println(a, b)

	s := []int{10, 20, 30}
	i := 0
	i, s[i] = 1, 99 // s[i] uses i from before the assignment: s[0] = 99
	fmt.Println(i, s)
}
```

The `&&` and `||` operators are evaluated **lazily**: the right operand runs only when needed, which makes guards like `p != nil && p.X > 0` safe.

## Summary

- `range` evaluates its expression once; arrays are copied, slices aren't.
- Map order is random on purpose; sort the keys when it matters.
- `range` over a string decodes UTF-8 and replaces invalid bytes with `U+FFFD`.
- `defer` belongs to the function, not the iteration.
- Only calls, channel receives and logical operators have a guaranteed order; don't mix side-effecting calls and reads in one expression.
