# Runtime: scheduler, memory, GC — Advanced

The design decisions of Go's GC: what it optimizes (latency, not peak throughput), why it's non-generational and non-moving, how `GOGC` interacts with `GOMEMLIMIT`, and how to diagnose memory problems.

## What Go's GC optimizes

GCs trade off three resources: **latency** (pauses), **throughput** (CPU consumed) and **memory**. Go's GC explicitly chose latency:

- stop-the-world pauses are kept under a millisecond, whatever the heap size;
- during marking, the GC uses about **25% of the CPU**, plus mark assist when the program allocates too fast;
- there aren't dozens of tuning knobs, as with the JVM: just `GOGC` and `GOMEMLIMIT`.

The price: a generational GC, which focuses on young objects, would use less CPU for programs that allocate a lot of short-lived data. Go compensates with **escape analysis** (many short-lived objects never reach the heap) and with pointer-free values (which don't need scanning).

## `GOGC` and `GOMEMLIMIT` together

The heap target for the next cycle is the **minimum** of the two criteria:

| Situation | Who decides |
|---|---|
| small live heap, far from the limit | `GOGC`: rare GCs, memory proportional to the live heap |
| live heap close to the limit | `GOMEMLIMIT`: more frequent GCs, so the total stays under the limit |
| live heap over the limit | the CPU limiter: the GC stays under ~50% of the CPU, memory exceeds the limit |

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	debug.SetGCPercent(-1)         // GOGC=off
	debug.SetMemoryLimit(64 << 20) // GOMEMLIMIT=64MiB
	var ms runtime.MemStats
	kept := make([][]byte, 0)
	for i := range 200 {
		b := make([]byte, 1<<20) // 1 MiB per iteration, of which we keep only some
		if i%10 == 0 {
			kept = append(kept, b)
		}
	}
	runtime.ReadMemStats(&ms)
	fmt.Printf("collections: %d, heap: ~%d MiB, kept: %d MiB\n",
		ms.NumGC, ms.HeapAlloc>>20, len(kept))
}
```

With `GOGC=off` and no limit, the program would never collect; with the 64 MiB limit, the GC starts only when needed.

## What Go's GC doesn't do

- **It isn't generational**: young objects aren't treated separately. Escape analysis makes up for much of this: most short-lived objects never reach the heap.
- **It doesn't compact**: objects aren't moved; size classes keep fragmentation in check.
- **Its pauses aren't proportional to the heap**: STW pauses depend on the number of Ps and active goroutines, not on heap size.

## Diagnosis

```bash
GODEBUG=gctrace=1 ./app                          # every cycle
go tool pprof http://host/debug/pprof/heap      # who holds memory (inuse_space)
go tool pprof -sample_index=alloc_space ...     # who allocates the most
go tool trace trace.out                          # GC, assists and pauses on a timeline
```

## Summary

- Go's GC optimizes latency: sub-1 ms pauses, ~25% CPU while marking.
- Non-generational and non-moving; escape analysis and pointer-free data compensate.
- The heap target is the minimum of the `GOGC` criterion and `GOMEMLIMIT`.
- Over the limit, the GC is capped at ~50% CPU to avoid a death spiral.
- `gctrace`, `pprof` (inuse/alloc) and `go tool trace` for diagnosis.
