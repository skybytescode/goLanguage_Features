# Runtime: scheduler, memory, GC — Practitioner

How to control the GC (`GOGC`, `GOMEMLIMIT`), how to read what it's doing (`gctrace`, `runtime/metrics`), and how to reduce pressure on it by writing code that allocates less.

## `GOGC`: the memory–CPU trade-off

The GC starts a new cycle once the heap has grown by a certain percentage over the **live** heap (what survived the last collection). That percentage is `GOGC`, **100** by default:

| `GOGC` | Live heap 100 MiB → next GC at | Effect |
|---|---|---|
| 50 | ~150 MiB | less memory, more CPU on GC |
| 100 | ~200 MiB | the default |
| 400 | ~500 MiB | more memory, less CPU on GC |
| `off` | never (only with `GOMEMLIMIT`) | — |

Doubling `GOGC` roughly doubles the extra memory and roughly halves the GC's CPU cost. It's set from the environment (`GOGC=200 ./app`) or from code (`debug.SetGCPercent(200)`).

## `GOMEMLIMIT`: the memory limit (Go 1.19)

`GOGC` is relative to the live heap, so it doesn't know the container's limit. If the live heap is 600 MiB and the container has 1 GiB, `GOGC=100` would let the heap grow toward 1.2 GiB → OOM kill.

`GOMEMLIMIT` is a **"soft"** limit on all memory managed by the runtime: as it gets close, the GC runs more often, regardless of `GOGC`.

```bash
# a 1 GiB container: leave headroom for stacks, off-heap buffers, etc.
GOMEMLIMIT=900MiB ./app

# a small heap, but you want to use the available memory without needless GCs:
GOGC=off GOMEMLIMIT=900MiB ./app
```

The limit is soft: if the live heap genuinely exceeds it, the runtime doesn't kill the program; it caps the CPU spent on GC (at most ~50%), to avoid a "death spiral" where the program does nothing but collect.

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	prev := debug.SetMemoryLimit(512 << 20)         // 512 MiB; returns the previous value
	fmt.Println("previous limit:", prev == 1<<63-1) // default: no limit
	fmt.Println("previous GOGC:", debug.SetGCPercent(150))
}
```

## What the GC is doing: `gctrace`

```bash
$ GODEBUG=gctrace=1 ./app
gc 7 @2.104s 3%: 0.031+4.2+0.044 ms clock, 0.25+1.1/8.3/12+0.35 ms cpu, 61->63->32 MB, 64 MB goal, 0 MB stacks, 0 MB globals, 8 P
```

| Fragment | Meaning |
|---|---|
| `gc 7 @2.104s` | the 7th cycle, 2.1 s after start |
| `3%` | the percentage of CPU used by the GC since start |
| `0.031+4.2+0.044 ms clock` | STW pause at start + concurrent mark + STW pause at end |
| `61->63->32 MB` | heap at start → heap at end → live heap marked |
| `64 MB goal` | the target for the next cycle |

Stop-the-world pauses are usually **under a millisecond**; marking runs concurrently with the program.

## `runtime/metrics`

For production monitoring, `runtime/metrics` offers stable metrics that are cheap to read (no stop-the-world, unlike `ReadMemStats`):

```go
package main

import (
	"fmt"
	"runtime/metrics"
)

func main() {
	samples := []metrics.Sample{
		{Name: "/gc/heap/live:bytes"},
		{Name: "/gc/cycles/total:gc-cycles"},
		{Name: "/sched/goroutines:goroutines"},
		{Name: "/memory/classes/total:bytes"},
	}
	metrics.Read(samples)
	for _, s := range samples {
		fmt.Printf("%-32s %d\n", s.Name, s.Value.Uint64())
	}
}
```

Go's Prometheus and OpenTelemetry exporters read these.

## Fewer allocations = less GC

The GC's cost grows with the **allocation rate** and the number of **pointers** to scan. Concrete techniques:

- **Preallocation**: `make([]T, 0, n)`, `make(map[K]V, n)`, `strings.Builder.Grow`.
- **Reusing buffers**: `sync.Pool`, or buffers supplied by the caller (`Read(p []byte)`).
- **Avoid needless conversions**: `[]byte` ↔ `string`, small values turned into `any` (for example logging arguments in hot loops).
- **Pointer-free structures**: a `[]Point` with `Point{X, Y int}` isn't scanned by the GC; a `[]*Point` has one pointer per element.
- **Values, not pointers**, for small structs (they stay on the stack).

Measure first: `go test -bench . -benchmem` shows `allocs/op`, and the allocation profile (`-memprofile`, see [Tooling](../../tooling/2/)) shows **where** you allocate.

## `GODEBUG`

`GODEBUG` controls runtime and compatibility options: `gctrace=1`, `schedtrace=1000`, `madvdontneed=1`, plus settings that keep old behavior after standard library changes (for example `http2client=0`). The defaults depend on the `go` line in `go.mod`; you can also pin them with `//go:debug` directives in the `main` package.

## Summary

- `GOGC` trades memory for CPU; 100 by default.
- `GOMEMLIMIT` is essential in containers; set it a little below the limit.
- `GODEBUG=gctrace=1` and `runtime/metrics` show what the GC is doing.
- Fewer allocations and fewer pointers = a cheaper GC.
- Measure with `-benchmem` and profiles before optimizing.
