# Runtime: scheduler, memorie, GC — Avansat

Deciziile de design ale GC-ului Go: ce optimizează (latența, nu throughput-ul maxim), de ce e non-generațional și non-moving, cum interacționează `GOGC` cu `GOMEMLIMIT` și cum diagnostichezi problemele de memorie.

## Ce optimizează GC-ul Go

GC-urile fac compromisuri între trei resurse: **latență** (pauze), **throughput** (CPU consumat) și **memorie**. GC-ul Go a ales explicit latența:

- pauzele stop-the-world sunt ținute sub o milisecundă, indiferent de dimensiunea heap-ului;
- în timpul marcării, GC-ul folosește în jur de **25% din CPU**, plus mark assist când programul alocă prea repede;
- nu există zeci de parametri de reglaj, ca la JVM: doar `GOGC` și `GOMEMLIMIT`.

Prețul: un GC generațional, care se concentrează pe obiectele tinere, ar consuma mai puțin CPU pentru programele care alocă mult și scurt. Go compensează prin **escape analysis** (multe obiecte de scurtă durată nici nu ajung pe heap) și prin valori fără pointeri (care nu trebuie scanate).

## `GOGC` și `GOMEMLIMIT` împreună

Ținta heap-ului pentru ciclul următor e **minimul** dintre cele două criterii:

| Situație | Cine decide |
|---|---|
| heap viu mic, departe de limită | `GOGC`: GC-uri rare, memorie proporțională cu heap-ul viu |
| heap viu aproape de limită | `GOMEMLIMIT`: GC-uri mai dese, ca totalul să rămână sub limită |
| heap viu peste limită | limitatorul de CPU: GC-ul nu depășește ~50% din CPU, memoria depășește limita |

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	debug.SetGCPercent(-1)         // GOGC=off
	debug.SetMemoryLimit(64 << 20) // GOMEMLIMIT=64MiB
	var ms runtime.MemStats
	pastrat := make([][]byte, 0)
	for i := range 200 {
		b := make([]byte, 1<<20) // 1 MiB per iterație, din care păstrăm doar o parte
		if i%10 == 0 {
			pastrat = append(pastrat, b)
		}
	}
	runtime.ReadMemStats(&ms)
	fmt.Printf("colectări: %d, heap: ~%d MiB, păstrat: %d MiB\n",
		ms.NumGC, ms.HeapAlloc>>20, len(pastrat))
}
```

Cu `GOGC=off` și fără limită, programul n-ar colecta niciodată; cu limita de 64 MiB, GC-ul pornește doar când e nevoie.

## Ce nu face GC-ul Go

- **Nu e generațional**: obiectele tinere nu sunt tratate separat. Escape analysis compensează mult: majoritatea obiectelor de scurtă durată nici nu ajung pe heap.
- **Nu compactează**: obiectele nu sunt mutate; fragmentarea e ținută în frâu de clasele de dimensiune.
- **Nu are pauze proporționale cu heap-ul**: pauzele STW depind de numărul de P-uri și de goroutines active, nu de dimensiunea heap-ului.

## Diagnoză

```bash
GODEBUG=gctrace=1 ./app                 # fiecare ciclu
go tool pprof http://host/debug/pprof/heap      # cine ține memoria (inuse_space)
go tool pprof -sample_index=alloc_space ...     # cine alocă cel mai mult
go tool trace trace.out                  # GC, assist și pauze pe axa timpului
```

## Pe scurt

- GC-ul Go optimizează latența: pauze sub 1 ms, ~25% CPU în timpul marcării.
- Non-generațional și non-moving; escape analysis și datele fără pointeri compensează.
- Ținta heap-ului e minimul dintre criteriul `GOGC` și `GOMEMLIMIT`.
- Peste limită, GC-ul e plafonat la ~50% CPU ca să evite „death spiral”-ul.
- `gctrace`, `pprof` (inuse/alloc) și `go tool trace` pentru diagnoză.
